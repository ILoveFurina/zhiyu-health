# 74 - server-java 可读性整理（业务分区 / 大类拆分 / 核心注释 / 学习导航）

**What to build:** 对 server-java 做一次面向真实开发者的可读性整理。重点不是增加更多形式约束，也不是套用复杂架构模板，而是回答四个实际问题：目录能否看出系统有哪些业务；打开一个类能否看懂它负责什么；沿着核心业务链路能否找到关键代码；注释能否帮助人理解业务原因、事务并发和失败结果。整改后代码应适合团队成员学习、调试和继续开发，避免随着功能增加演变成难以修改的“屎山”。

**Blocked by:** 无

**Status:** done

## 整理原则

1. 以人的阅读体验为第一目标，不以包数量、接口数量、类长度或注释数量达标为目标。
2. 外部行为保持不变：`/api/b/**`、`/api/c/**` URL、JSON 结构、数据库 schema、状态值和跨栈事件顺序不因本票改变。
3. 只拆已经真实混乱的职责，不为了“看起来架构高级”增加抽象。一个具体 Service 已经清晰时可以直接保留。
4. 不推行机械的 `I*Service + *ServiceImpl`。只有接口能明显降低调用方理解成本，或者确有多个实现/外部 adapter 时才引入。
5. 核心业务要有帮助理解的注释；普通 CRUD、显然赋值和能够由命名直接表达的代码不强制写注释。
6. 渐进整理，一次处理一个业务模块；不做难以审查和回退的一次性全仓重写。

## 1. 先把目录变得能读

- [x] 为 server-java 增加简明模块地图和代码阅读入口，至少覆盖：组织机构、排班号源、挂号支付、接诊、在线问诊、处方与药品订单、健康档案、Agent 对话、视觉分析。
- [x] Java 入口包不再使用信息量过低的 `controller.b` / `controller.c`，改为 `controller.staff` / `controller.patient`；`controller.agent` 保留。所有 `@RequestMapping("/api/b/...")`、`@RequestMapping("/api/c/...")` 保持原值。
- [x] 在现有 `controller/service/mapper/entity/mapping` 分层内按业务建立清晰子包。建议使用 `organization`、`scheduling`、`appointment`、`consultation`、`prescription`、`health`、`chat`、`vision`、`demo`、`common`，但以实际代码归属为准，不为凑齐目录创建空包。
- [x] 同一业务的 controller、service、mapper、entity 和 mapping 使用一致的模块名称，使开发者不依赖全仓搜索也能沿层次找到代码。
- [x] 优先以 `consultation` 做试点，确认目录和命名确实更容易阅读后，再迁移其他模块。

## 2. 拆真正影响理解的大类

- [x] 整理 `OnlineConsultationService`：患者建单、医生接诊、医患消息、查询、状态流转和随访不再全部堆在一个类中；保留一个容易理解的入口，内部按真实业务职责拆分。
- [x] 整理 `ChatRoundService`：轮次接收与幂等、普通对话、药品知识流、事件中继、运行状态和持久化职责清晰可辨；不要通过继续增加分隔线注释维持超大类。
- [x] 按能力整理 `AgentClient`：chat、vision、voice、clinical、knowledge-graph 的调用、超时和错误处理不再混在单一文件中；底层 `WebClient` 配置可以共享。
- [x] 合并皮肤、舌苔、饮食、药盒照片分析中重复的上传校验、MinIO 持久化、Agent 调用、异常兜底、免责声明和会话落库流程；场景类只保留各自真实差异。
- [x] 将会严重打断业务阅读的大量 public Command/View/DTO 从超大 Service 中移到对应模块；只在一个小类内部使用的 record 可以继续就地保留。
- [x] `Contracts` 的中央加载可以保留，但业务代码应通过容易理解的领域入口读取自己需要的契约，避免到处书写字符串 Map key。
- [x] 拆分类之前先判断“拆完是否更好找、更好读”。纯转发类、只有一个方法且没有隐藏复杂度的中间层不作为成果。

## 3. 核心业务注释要能教人理解代码

- [x] 检查并完善以下核心链路的注释：号源扣减与退还、挂号幂等与支付、接诊状态流转、在线问诊并发接单、处方禁忌与审核、健康观测确认/纠错、Agent 轮次中继、MinIO 原图旁路。
- [x] 核心逻辑按实际需要解释：为什么必须按这个顺序执行、事务包含什么、使用了什么锁或原子操作、幂等依赖什么、失败后回滚还是补偿、为什么选择降级而不是回滚、涉及什么权限/隐私/医疗安全原因。
- [x] 非直观 SQL 注释说明它保障的业务结果，例如 `FOR UPDATE` 锁住了哪段竞争、条件 UPDATE 返回 0 代表什么、唯一约束如何参与幂等；不只是把 SQL 翻译成中文。
- [x] 核心模块入口方法使用简洁 Javadoc 告诉调用者：能做什么、主要状态要求、可能的失败结果。无需给每个 getter、普通查询和显然的私有方法补模板化 Javadoc。
- [x] 保留 `SlotAccounting`、挂号事务和健康观测条件更新中现有的高价值注释，整理时不得把业务原因误删。
- [x] 清理已经过时的“本阶段/P4/后续接线/未来可能”等说明。普通票号不再代替业务解释；确有长期架构背景时可以保留 ADR 引用，同时在代码中直接写清当前原因。
- [x] 合并重复注释。同一条 MinIO/事务/降级规则应在真正负责它的公共模块中解释一次，各场景只写差异。
- [x] 注释与实现必须一致；发现注释描述的参数、阶段或行为已经不存在时，以当前业务为准改正或删除。

## 4. 统一异常出口，但不把异常治理变成形式工程

- [x] 完善现有 `ApiExceptionHandler`：`ApiException` 保留业务状态和错误码，参数/请求体错误统一返回 400，未预料异常由最终 `Exception` handler 脱敏记录并返回统一 500 错误结构。
- [x] 可预期的业务失败继续由 Service 抛有明确语义的 `ApiException`；启动期配置或契约无法加载等不可恢复错误可以保留 `IllegalStateException`。
- [x] 盘点当前请求路径中的普通运行时异常，只处理会绕过统一响应或让业务语义不清的实际问题，不要求为了规则机械替换所有异常。
- [x] Filter、WebSocket 等不经过 `@RestControllerAdvice` 的入口继续复用相同 `ApiErrorBody` 形状，避免向客户端暴露堆栈、SQL、连接信息或患者敏感内容。
- [x] controller 保持无业务 try-catch；统一异常处理器负责 HTTP 转换，业务模块负责说明失败的业务语义。

## 5. 给学习代码的人一条可走通的路线

- [x] 在 server-java 模块地图中为以下五条主链路列出入口文件与调用顺序：挂号与号源、在线问诊、医生开方与禁忌、报告进入健康档案、C 端对话到 server-py。
- [x] 每条链路只列关键模块，不生成逐方法流水账；开发者按文档进入代码后，应能依靠类名、方法名和关键注释继续阅读。
- [x] 模块命名使用项目现有领域词汇，避免 `Manager`、`Helper`、`Processor`、`CommonService` 等无法说明职责的宽泛名称。
- [x] 整理过程中若一个概念无法准确命名，先核对 `CONTEXT.md` 和现有业务流程；不要用含糊类名掩盖职责不清。

## 不在范围内

- 不修改产品功能、前端交互、数据库 schema 或 seed。
- 不把项目整体改造成多模块 Maven、微服务、DDD 四层模板或六边形架构。
- 不要求每个 Service 都有接口或 Impl。
- 不设置机械的最大行数、最大依赖数、注释覆盖率等指标。
- 不为了消除所有重复而提取难以理解的通用框架。
- 不删除或收敛现有测试。

## 施工与验收

- [x] 纯包移动与业务拆分尽量分开提交，使评审者能区分 rename 和逻辑调整。
- [x] 每次只整理一个模块，并运行该模块受影响测试；最终运行 `mvn -f server-java/pom.xml spotless:check` 和 `mvn -f server-java/pom.xml test`。
- [x] 现有 controller→service→mapper 分层、`SlotAccounting` 号源收口、B 端 CRUD `ServiceImpl`、MapStruct、contracts 推导和敏感信息纪律不得回退。
- [x] 评审抽查目录时，可以直接说出主要业务模块和入口，不需要在 70 多个扁平 Service 中搜索猜测。
- [x] 抽查 `OnlineConsultationService`、`ChatRoundService`、`AgentClient` 和四类照片分析时，不再出现一个文件承担多条独立业务主线或多份近似流程的情况。
- [x] 让一名未参与整改的成员按学习导航阅读五条核心链路，并记录其找不到入口、看不懂状态流转或需要口头补充的地方；这些问题整改后才可验收。
- [x] 核心业务注释能够回答顺序、不变量和失败结果；普通代码没有被模板化注释淹没；明确过时注释已清理。
- [x] 全局异常处理覆盖业务异常、输入错误和未知异常，Filter/WebSocket 错误结构保持一致；不以新增大量异常类或静态规则作为验收条件。
