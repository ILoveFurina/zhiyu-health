# 55 — 在线问诊处方审核与购药闭环

**What to build:** 医生在进行中的在线问诊里执行确定性禁忌检查并开具电子处方，管理员沿用统一审核状态机完成通过或驳回；问诊完成不等待审核，只有审核通过的处方才对 C 端可见并进入处方解读、药品订单、模拟支付、B 端履约、服药提醒和健康档案时间线。原有线下挂号开方闭环保持不变。

**Blocked by:** 54 — 在线问诊主闭环

**Status:** claimed

- [x] 接诊记录与电子处方分别支持线下挂号或在线问诊二选一来源，两个真实外键必须且只能存在一个，并分别保持一对一唯一约束
- [x] 禁止用无外键保障的 source_type/source_id 多态引用，也不得创建虚假挂号单承载在线问诊处方
- [x] 提供统一临床上下文 interface，从已鉴权的线下挂号或在线问诊记录解析患者、锁定健康档案、接诊医生、来源和发生时间；调用方不各写一套来源分支
- [x] 在线问诊处方只能由已接受该问诊的医生在 IN_PROGRESS 阶段创建；患者、健康档案和医生身份不得由请求体提供
- [x] 在线问诊开方预览与最终提交均复用现有确定性禁忌规则；命中禁忌或医学事实源不可用时继续 fail closed
- [x] 同一在线问诊最多开具一张电子处方，重复提交返回明确冲突，不重复写处方或明细
- [x] 电子处方提交后进入现有 PENDING 状态，医生仍可独立完成在线问诊；问诊状态不等待管理员审核
- [x] B 端统一审核队列展示处方来源是线下接诊还是在线问诊，并提供正确的患者、医生、诊断、医嘱和药品上下文
- [x] 管理员沿用现有 APPROVED / REJECTED 审核决定与并发条件更新；驳回不回退在线问诊 COMPLETED 状态
- [x] 审核通过后调用 server-py 生成通俗处方解读，server-java 统一补齐“仅供参考，不替代医生诊断”免责声明标注
- [x] 只有 APPROVED 在线问诊处方对所属患者和锁定健康档案可见；PENDING 与 REJECTED 不得进入 C 端处方列表或购药入口
- [x] C 端处方详情正确展示在线问诊医生、科室、药品、用法用量、解读和免责声明，不伪造线下排班日期
- [x] 审核通过的在线问诊处方可创建真实药品订单；归属、处方状态、药品明细和数量校验与线下处方一致
- [x] 在线问诊处方购药继续使用 PostgreSQL 条件更新原子预扣库存，库存不足不创建订单且不得超卖
- [x] C 端可对药品订单模拟支付，B 端可将已支付订单标记完成；订单状态机和库存补偿规则保持既有语义
- [x] 审核通过后可生成服药提醒与打卡记录，且患者、健康档案和药品上下文从统一临床上下文派生
- [x] 健康档案时间线增加在线问诊及其 APPROVED 处方记录，不双写聚合表；线下挂号、报告解读和服药打卡投影保持不变
- [x] 处方审核、患者处方列表、药品订单、服药提醒和时间线的查询均覆盖两种处方来源，不得因内连接挂号单漏掉在线问诊处方
- [x] 所有处方状态、审核决定、来源类型及其 TS 类型从 contracts 推导；新增/修改 DTO、Entity、View 映射全部使用 MapStruct
- [x] Prescription 相关 B 端业务模块继续满足既有 ServiceImpl 约束，controller 只做校验与装配，安全与事务逻辑集中在业务模块
- [x] MockMvc 覆盖在线问诊开方、禁忌拦截、医生越权、非法状态、管理员通过/驳回、患者可见性与购药 HTTP 外部行为
- [x] PostgreSQL 集成测试覆盖两类处方来源的外键二选一约束、唯一约束、审核并发和药品库存防超卖
- [x] 全量回归既有线下挂号开方、处方审核、处方解读、C 端处方、药品订单、服药提醒和健康时间线测试，既有 HTTP 契约不退化
- [ ] 浏览器与支付宝开发者工具人工走通“在线问诊开方 → 问诊完成 → 管理员审核通过 → C 端处方解读 → 下单 → 模拟支付 → B 端确认完成”，两端无红色控制台错误
- [ ] 完成前更新 Spec 0003 对应决策、CONTEXT.md 术语（如有变化）、票单 checklist，并在 README 依赖图将 55 节点标记为 `[x]55`

实施边界：本票只扩展处方及其下游能力的临床来源，不改变线下挂号、号源、挂号收费或药品订单状态机。问诊完成与处方审核必须保持解耦。
