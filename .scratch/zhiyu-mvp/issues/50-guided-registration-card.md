# 50 - 智能导诊标准科室与科室号源卡

**What to build:** 修复智能导诊“科室已经明确仍继续询问、科室号源卡没有出现”的断链。在票 49 的动态服务城市、标准科室接口和可复用号源卡组件上接入对话：用户明确表达科室挂号意图，或多轮导诊已形成单一明确标准科室后，由编排代码保证自动查询 server-java 只读号源能力，不依赖 LLM 自行决定是否调用工具；先展示由号源结果确定性生成的简短摘要，再在同一会话内展示未来 14 天的跨医院科室号源卡。不得再用“需要我帮你查附近医院或有号医生吗”等无法保证执行的话术。

**Blocked by:** 18 - 红线症状（已完成）；31 - 对话主干双栈化（已完成）；49 - AI挂号助手动态城市与确定性自助挂号

## Comments

- 2026-08-06：由 `grill-with-docs` 会话确认。AI挂号助手主卡是入口卡；本票科室号源卡是标准科室确定后的 Agent 业务数据出口，两者不得混用。
- Agent 只确定标准科室；城市、医院、院区、医生、距离、排班、余号与挂号仍由 server-java 确定性处理。
- 2026-08-07：根据截图复现确认当前断链有两层：现有 prompt 把工具调用限制为“科室明确且用户需要医生推荐”，导致科室明确后仍会空口询问；票 49 科室号源卡目前只接入自助挂号页面，尚无对话 SSE 出口。决定改为编排层强制查询，并由代码基于卡片数据生成摘要。
- 2026-08-07：本票不处理 B 端医生工作台，也不改动现有安全机制；相关产品边界另行讨论，不得借本票扩大范围。
- 2026-08-07：三栈实施完成（分支 t50-guided-registration-card）。要点：科室解析为结构化二次 LLM 判定（照 emotion 范式），explicit_booking/resolved 由 `AgentChatService` 编排层强制查询，LLM 不参与摘要措辞；server-java 目录回调返回 `{departments:[...]}` 包装；查询失败以 `department_slots` 卡 `status=failed` 呈现普通失败消息与重试（持久化可回放），重试经 `retry_standard_department_id` 跳过解析直查；号源卡 `earliest_bookable` 取消 @JsonIgnore 并补 `campus_address`。行为变化：schema.sql 新建 `ck_messages_kind` CHECK（契约 kind 全量 + red_flag），开发期 drop+recreate 无影响。server-py 套件仅 2 条 knowledge 集成测试失败（需云端 pgvector 回填数据，知识链路本票未改动，属环境性预存失败）。剩余：支付宝开发者工具实测与 README 标记。
