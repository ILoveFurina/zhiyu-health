# 75 - server-py 可读性与核心业务模块化治理（代码导读 / 主链路拆分 / 核心业务注释）

**What to build:** 在不改变 HTTP 路径、跨栈契约、SSE 事件顺序、模型安全边界和现有业务行为的前提下，整理 server-py 随功能迭代形成的主链路堆积问题。整改以“项目成员能够顺着代码真正学懂业务”为目标：目录名能够预测内容，核心流程能够沿少量入口文件读通，注释解释业务意图、关键规则、失败与降级语义；不追求机械分层、文件越短越好或为类型检查增加大量样板。

**Blocked by:** 无

**Status:** done

## 现状判断

- server-py 整体尚未成为全面“屎山”：`api/` 基本保持薄入口，`schemas/` 职责明确，`agent/vision/` 已形成“文档规范化 → 场景策略 → 模型解读”的清晰范例，知识检索和结构化 judge 也较易单独阅读。
- 对话主链路已形成高风险热点：`services/chat.py` 同时承载知识源选择、导诊收敛、号源直查、情绪判断、预问诊摘要、SSE 事件组装、后台任务与免责声明；`agent/runner.py` 同时承载 LangGraph 执行、消息转换、工具 trace、脱敏和卡片投影。
- `tools/business.py` 同时包含 HTTP 客户端、错误转换、普通业务回调、摘要回调和 LLM 工具；`main.py` 同时维护生产/测试两套装配并通过大量动态 `app.state` 字段传递依赖，入口不适合作为新人阅读起点。
- 注释数量充足但质量不均：安全边界、确定性规则、隐私和失败降级说明价值较高；大量“票 44/50/55/62/65”等施工历史挤入核心代码，并已出现向量维度 1024/2048、入口能力说明等失真注释。
- 立票时 `ruff`、`mypy`、`lint-imports` 均通过；`uv run pytest -q` 为 202 passed / 2 failed，失败来自知识检索集成测试仅凭 `.env` 凭据存在便自动访问真实方舟与 pgvector。默认测试不应隐式触发外部调用。

## 整改原则

1. 以人的阅读路径为第一优先级，不以文件行数、接口数量、注释数量作为独立目标。
2. 核心业务必须有注释；注释重点回答“为什么这样做、必须保证什么、失败后怎样”，不逐行翻译代码。
3. 长文件若职责单一且阅读连续，可以保留；只有多个业务原因会分别导致其变化时才拆分。
4. 对外保持小而稳定的入口，拆分细节藏在模块内部；不得新增只有一行转发逻辑的空壳层。
5. 不为追求零 `Any` 或形式上的绝对分层进行全仓模型化；优先给跨模块核心业务数据和事件补充清晰命名。
6. 渐进施工，一次只整理一条可回归的业务链路，不做一次性全仓搬家。

## 实施范围

### 1. 建立面向学习的 server-py 代码导读

- [x] 新增 `server-py/README.md`，说明 server-py 的职责边界、目录地图、启动/测试命令和推荐阅读顺序。
- [x] 用一张简洁调用链说明普通对话：`api.agent → 对话编排 → Agent runner → tools/knowledge → SSE`。
- [x] 分别说明智能导诊、预问诊、视觉解读、语音、临床文本生成和知识检索六条核心业务链路；每条列出入口、核心模块、外部依赖、确定性规则与降级结果。
- [x] 明确哪些内容由 server-java 决定，哪些内容允许 LLM 生成，避免学习者仅看 Python 代码后误解医疗安全边界。
- [x] 文档只做导航和关键设计说明，不复制大段实现代码；文件移动时同步维护。

### 2. 整理对话主链路

- [x] 将 `AgentChatService` 收口为容易阅读的对话总流程入口；主方法按业务阶段清楚呈现：推理档位 → 确定性导诊/号源分支 → 知识增强选择 → Agent 流 → 最终消息/卡片 → 非关键后台摘要。
- [x] 把智能导诊与号源卡逻辑整理为独立内部模块，集中表达科室收敛、重复卡抑制、确定性摘要、失败卡和事件顺序。
- [x] 把预问诊摘要整理为独立内部模块，集中表达何时调度、为何不阻塞 `done`、失败为何保留上一版以及回调的隐私纪律。
- [x] 把知识源选择与降级事件整理为独立策略模块，读者无需进入 LangGraph runner 即可理解 rag/graph/none 的选择规则。
- [x] 把 Agent 输出到项目 SSE 事件的转换集中到单一位置，免责声明、thinking、tool trace、knowledge 和卡片事件的投影规则不再散落。
- [x] 对外 HTTP 请求字段和 SSE 事件形状保持不变，不改变 server-java 与端侧行为。

### 3. 整理 Agent runner 与业务工具

- [x] `agent/runner.py` 聚焦 LangGraph 模型/工具装配和流式执行；工具 trace、结果脱敏、卡片/知识事件映射移入命名明确的内部模块。
- [x] 将 `AgentContext`、`AgentOutput`、健康档案上下文等主链路共享概念放到无需跨层反向引用的位置，使学习者能先读懂项目概念再读实现。
- [x] `tools/business.py` 聚焦提供给 LLM 的业务工具；HTTP 回调通道、公共错误转换和预问诊摘要回调按职责整理，普通模块不再引用其他模块的私有辅助函数。
- [x] 保留生产实现与 fake 的可替换能力，但不机械新增 `Protocol`、抽象基类或一一对应实现类。
- [x] 保持工具失败不掐断 SSE、患者/会话/定位由可信运行上下文注入、敏感原文不进入 trace 等现有核心规则。

### 4. 简化应用入口与模块导航

- [x] `main.py` 只保留事件循环准备、FastAPI 创建、路由挂载和 lifespan 接入等入口职责；生产依赖构建与测试依赖装配从主入口中清晰分开。
- [x] 收拢当前大量 `create_app()` 可选参数和动态 `app.state` 字段，使测试注入条件显式，不再依赖“必须先传 health_service 才进入测试路径”的隐藏知识。
- [x] 盘点 `api/`、`agent/`、`tools/`、`services/`、`db/`、`core/` 的实际内容，修正文档和模块说明；不要求为了形式统一而迁移职责清楚的模块。
- [x] 以 `agent/vision/` 现有结构作为正向样例，保留其“输入准备 / 场景策略 / 模型解释”清晰分工，不做无收益重写。

### 5. 核心业务注释治理

- [x] 核心模块文件头说明：本模块解决什么业务问题、主要输入输出、明确不负责什么，以及关键安全/降级边界。
- [x] 核心主流程在重要阶段和非直观分支前写业务注释；普通赋值、循环、显然校验和 getter 不要求注释。
- [x] 必须保留或补齐以下高价值说明：确定性规则与 LLM 的分工、免责声明注入、工具失败降级、科室/号源事实来源、预问诊异步一致性、隐私脱敏、视觉范围限制、语音 fake/disabled 选择、RAG/图谱空召回语义。
- [x] 将生产代码中的普通票号注释改写为当前业务规则；确需追溯时在业务说明后附 issue/ADR，不得以“票 55”代替原因。
- [x] 删除重复、过时和施工阶段型说明，修复已发现的 vector 1024/2048、`main.py`“只挂两类接口”等事实漂移。
- [x] 注释自然形成多个互不相关的大章节时，优先拆分模块，禁止继续用大段注释掩盖多职责文件。

### 6. 测试作为学习材料整理

- [x] 将超大的 `test_vision_api.py` 按报告、皮肤、饮食、舌象、药盒和文件校验拆分；公共 fake/样例集中放置，测试名保持业务语言。
- [x] 视整改落点拆分 `test_chat_api.py`、`test_preconsultation.py` 和 `test_guided_registration.py`，让读者可以按业务场景查找示例。
- [x] 知识检索真实集成测试改为显式环境变量或 pytest marker 门控；默认 `uv run pytest` 不读取真实凭据发起外部模型/数据库调用。
- [x] 重构测试应通过模块公开入口断言可观察行为，避免把新的内部文件结构写死在测试里。

## 施工纪律

- [x] 先以注释清理和代码导读建立共同理解，再拆对话主链路；不得在不了解现有降级语义时直接移动分支。
- [x] 一次提交只处理一个可描述的主题，例如“提取导诊流程”“拆 runner 事件投影”“整理业务回调”“重写核心注释”。
- [x] 纯移动与业务修改尽量分开，便于 Git 识别 rename 和人工审查。
- [x] 不修改 HTTP path、JSON 字段、契约值、提示词医疗边界、SSE 顺序、免责声明、数据库 schema 或 server-java 行为；发现功能缺陷另开票处理。
- [x] 不删除为了医疗安全、失败降级、隐私保护和跨栈一致性建立的存量测试。
