# 49 - AI挂号助手：动态城市与确定性自助挂号

**What to build:** 将现有“找医院 + C 端预约挂号”重构为不依赖 Agent 的 AI挂号助手确定性底座：服务城市动态产生，医院按城市硬过滤并以最近院区距离排序；患者可从主卡或首页按医院/标准科室选择院区、实际科室、医生和未来 14 天号源。服务城市、医院、院区、科室、医生、排班和挂号共用同一套 PostgreSQL 业务数据，城市与郑州演示值均不得写死。

**Blocked by:** 29 - 组织管理迁移（已完成）；30 - 排班号源迁移（已完成）；42 - 小程序首页与 tabBar（待人工验收）

**Status:** ready-for-agent

## 1. 数据模型与 B 端管理

- [ ] `schema.sql` 建立 `hospital_campuses`、医院自定义科室分类、平台“科类 → 标准科室”目录；实际科室归属具体院区和医院分类，并以非空外键映射标准科室；医院不再承载院区地址/坐标语义
- [ ] 院区维护结构化 `city_code`、`city_name`、虚构地址、经纬度；服务城市由现有院区动态聚合，禁止在前端或查询 SQL 中写死郑州市
- [ ] seed 改为 3 家郑州虚构医院：郑州智愈综合医院（主院区/郑东院区/南院区）、郑州智愈儿童医院（西院区/东院区）、郑州智愈中心医院（主院区）；现有虚构医生与科室合理分配到院区，排班扩展为今天起连续 14 天
- [ ] B 端补齐医院、院区、医院科室分类、实际科室及标准科室映射的管理界面；新 CRUD service 继承 `ServiceImpl`，DTO/Entity/View 映射使用 MapStruct
- [ ] 全链外键限制删除、禁止级联删除；无下游关联允许删除，存在院区/科室/医生/排班/挂号时由 server-java 返回明确 409，不产生孤儿数据
- [ ] 挂号单、就诊指引卡及历史列表继续能从排班追溯到正确院区地址，不得从医院旧地址字段兜底

## 2. server-java 确定性目录与号源

- [ ] 提供动态服务城市、当前城市医院列表、医院院区、院区科室、城市标准科室目录、跨医院标准科室号源接口；医院列表按医院去重，以最近院区距离排序
- [ ] 当前城市是医院与号源查询的硬筛选边界；无本城市数据时返回空结果，不跨城市推荐远距离医院
- [ ] 标准科室号源统一返回今天起连续 14 个自然日、医生、医院、最近院区、距离、上午/下午排班和余号；不实现普通号、专病门诊或医生跨院区/跨医院执业
- [ ] 全部号源按最早可约日期/时段后最近院区排序；指定日期时按最近院区后上午/下午排序；稳定医生 ID 兜底，避免刷新跳动
- [ ] 无论是否有号都返回同一种结构：有号医生优先，无号医生保留并禁用预约；所有数量与最早可约时间由 server-java 计算

## 3. C 端 AI挂号助手与自助挂号

- [ ] 小程序启动时提供可跳过的就医位置确认；使用 `my.chooseLocation` 获取城市与经纬度并仅保存在本次小程序会话，允许重新校正，拒绝时不影响其他功能且不展示距离
- [ ] 实现“AI挂号助手 · {当前城市}”主卡：无副标题，仅含“科室挂号”“智能导诊”两个入口、最近 3 家平台医院和真实总数；城市标题与医院数据禁止写死
- [ ] “科室挂号”进入城市级“科类 → 标准科室”左右目录与搜索；医院入口进入“医院 → 院区 → 实际科室”目录
- [ ] 对话主卡与首页“预约挂号”共用 service、组件和后续流程，不复制业务状态；原“找医院 → Agent”链路停止作为自助入口
- [ ] 自助流程收口为“城市 → 医院或标准科室 → 院区/实际科室 → 医生 → 14 天号源 → 确认挂号”；选中医生后只展示医生信息和上午/下午时间，不再选择医院或院区
- [ ] 建立可复用科室号源卡组件：14 天日期、有号/无号医生、医院与院区、距离、余号和预约按钮；无号医生按钮置灰，为票 50 的 Agent 卡片出口复用
