## Comments

### 2026-07-29 — Grilling 决策记录

- 报告解读是独立持久化记录，可选关联发起它的会话；上传过程与结构化解读卡片在会话中呈现。没有会话时，在提交文件时惰性创建会话。
- 原始图片或 PDF 仅在处理期间临时持有，处理完成或失败后立即清理，不持久化原件。数据库只保存患者/会话关联、原文件类型、页数、脱敏展示名、结构化结果、处理状态、失败原因码、免责声明标注与时间信息。
- ticket 12 使用单次同步处理链路：C 端上传至 server-java，server-java 校验并转发 server-py，server-py 返回结构化解读，server-java 持久化后返回卡片；不建设异步任务、轮询或断点恢复机制。
- PDF 采用逐页三级路由：连续正文且文本层可靠时使用抽取文本；表格、图表、多列或混合页同时提交抽取文本与受控分辨率页面图像；扫描页或损坏文本层仅提交页面图像。路由由可测试的确定性策略完成，不交给 LLM 决定；各页保持原顺序后生成一份整体解读。
- 报告解读卡片采用红/黄/蓝/绿四级关注优先级：红色表示建议尽快咨询医生或复查，但不等同于急救警报；黄色表示重点关注并按期复查；蓝色表示日常观察或生活方式改善；绿色表示报告所示范围内暂未见明显异常。拨打 120 和中断流程仍仅由 server-java 红线症状规则触发，报告模型无权触发。
- 每个关注项包含项目名称、报告原值、参考范围、单位、关注级别、通俗解释、建议动作与来源页码；顶层包含整体摘要、重点关注项、健康行动清单、无法可靠识别项和免责声明标注。模型不得补全看不清或原报告不存在的数值。
- 公共视觉管道只接受受控场景枚举，不接受 C 端或 server-java 传入任意 prompt。server-py 内部按场景注册系统提示词、结构化输出 Schema、预处理策略、安全约束与结果校验器；ticket 12 只实现 `REPORT`，后续票再注册药盒、皮肤、饮食与舌苔场景。
- MVP 上传限制：单次 1–5 张 JPEG/PNG，单张不超过 10MB、图片总量不超过 20MB；PDF 为单个 10MB 以内文件且最多 20 页。拒绝加密、损坏或空白 PDF；限制解码后的最大像素数并等比缩放超大图片，PDF 以受控分辨率栅格化；超出限制时明确提示拆分上传，不静默截断。
- server-py 对模型输出执行严格的结构化 Schema 校验；首次失败时携带校验错误进行一次受控重试，仍失败则返回稳定错误码。server-java 将其记为失败，只保存错误码和脱敏摘要，不保存模型原始输出；C 端不展示部分结果，提示用户重新上传。模型超时、文件不可读、输入超限与输出非法使用不同错误码。
- 报告解读同时保存业务记录与会话卡片快照：`report_interpretations.result_json` 供健康档案使用，消息 `content` 保存用户当时看到的不可变卡片 JSON供会话回放；消息类型为 `report_upload` 与 `report_interpretation`，并关联报告解读记录。删除会话只删除消息快照，不删除独立报告解读记录；卡片原始 JSON 不直接进入 LLM 最近上下文。
- 报告解读完成后支持在同一会话继续追问。系统从校验通过的结构化结果中确定性生成受限长度的报告上下文摘要，供后续 LLM 上下文使用但不在 C 端重复展示；摘要不通过第二次 LLM 调用生成，新建或切换会话后不自动带入。
- 安全目标不是阻止模型接触全部健康信息：报告解读所必需的指标、数值、参考范围以及必要的年龄/性别信息允许进入火山方舟；姓名、身份证号、手机号、就诊卡号等非必要直接身份标识应尽可能在本地移除。原始输入与模型原始输出不得进入审计日志或 Agent trace，演示只使用虚构报告。未来处理真实报告前，须补齐明确授权并核实模型供应商的数据保留、训练与删除条款。
- C 端在聊天输入框最右侧增加圆润美观的 `+` 按钮，点击后提供拍摄报告、从相册选择、上传 PDF 三种入口。选择完成后先展示可取消的待发送卡片，用户明确点击发送后才上传；ticket 19 的“看报告”功能气泡后续复用同一上传组件。
- 首次使用报告解读时展示一次明确确认：报告内容将发送至火山方舟多模态模型处理，用户须确认有权上传，并建议遮盖姓名、身份证号、手机号和就诊卡号，同时展示免责声明标注。确认结果留在本地；后续上传不重复弹窗，但待发送卡片保留轻量隐私提醒。拒绝不影响其他功能。
- ticket 12 不宣称或实现图片自动脱敏。文件展示名与持久化文件名脱敏，文字型 PDF 抽取文本后以确定性规则遮盖明显的身份证号、手机号和就诊卡号；图片与扫描 PDF 提示用户上传前自行遮盖，演示仅使用虚构报告。可靠的图片脱敏需未来单独引入本地 OCR、字段定位、打码预览与用户确认。
- 报告解读使用独立、无工具权限的多模态模型调用，只复用模型适配层，不进入主对话 LangGraph 工具循环。报告图文一律视为不可信数据而非指令，禁止调用业务工具、访问文档中的二维码/链接或输出 Schema 以外内容；报告完成后的追问再交由普通会话 Agent 处理。
- `REPORT` 场景只支持检验/化验单、体检报告，以及超声、CT、MRI、X 光等检查的文字结论页；不支持 DICOM、原始 CT/MRI 序列或单独的 X 光片、超声切面等医学影像诊断。超出范围时拒绝生成诊断并提示上传文字报告页；皮肤、舌苔等照片由后续独立场景处理。
- C 端每次确认发送时生成 `request_id`，server-java 对患者与请求 ID 建唯一约束，并以 `PROCESSING → SUCCEEDED | FAILED` 状态机保证幂等。成功请求的重复提交返回已保存卡片，处理中不并发调用模型，失败后只有用户明确重试才生成新请求 ID；超时或异常须落为稳定失败状态，避免重复计费和重复记录。
- 当前 MVP 不提供报告解读记录的删除 UI 或删除 API，也不将删除能力作为 ticket 21 的延期事项；原始图片/PDF 仍不持久化，报告解读结构化记录持续保留。
- 验收包含自动化 fake 与少量真实火山方舟 smoke：使用虚构的单张检验单图片和同时包含文字页、扫描页的虚构多页 PDF，验证数值/参考范围/页码识别、结构化 Schema、四级卡片、免责声明标注和同一会话追问。日常自动化测试不调用真实 API，任何测试不得记录报告原文或凭据。
- 一次上传只表示一份报告；选择的 1–5 张图片按用户确认的顺序视为该报告的连续页面，可在待发送卡片中调整顺序或移除。ticket 12 不做多日期报告趋势比较、自动拆分多份报告或一次生成多条报告记录。
