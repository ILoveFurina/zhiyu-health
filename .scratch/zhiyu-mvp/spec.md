# 智愈 MVP 规格（Spec 0001）

Status: ready-for-agent
日期： 2026-07-27 · 周期： 两周（约 14 日历天）· 团队假设： 3–5 人，三线并行（小程序 / B 端 / 后端+AI）

## Problem Statement

患者就医前不知道挂什么科、挂哪个医生，流程繁琐且无人引导；医生接诊前对患者一无所知，诊疗效率低。题目要求构建 B+C 深度联动的医疗平台：C 端 AI Agent 不是问答机器人，而是能调用 API 完成真实业务闭环（挂号、下单、预约）的智能助手；B 端为 Agent 提供数据支撑并赋能医生。评审交付场景：可现场演示的完整业务闭环 + AI 创新亮点。

## Solution

支付宝原生小程序（C 端）：医疗 AI Agent 完成"症状描述 -> 追问 -> 科室 -> 医生推荐 -> 挂号"全闭环，全程情感化交互（情绪识别、主动关怀、语音多模态），并附处方解读、报告解读、健康档案。React（Umi + Ant Design）Web 管理后台（B 端）：医院/科室/医生/排班/号源管理，医生工作台（接诊台看病情摘要、开电子处方），医学知识图谱可视化，数据看板。后端双栈（ADR-0009）：Java 业务后端（server-java，Spring Boot + MyBatis-Plus，唯一对外入口与唯一业务写入方）+ Python Agent 层（server-py，FastAPI + LangChain + LangGraph，对话编排与知识检索），存储 PostgreSQL+pgvector / Redis / Neo4j（ADR-0003、0006），LLM 用火山方舟 doubao（ADR-0004），Agent 编排 LangChain + LangGraph（ADR-0005）。

## User Stories

**C 端（患者）**

5. 作为患者，我想收到结构化医生推荐卡片（照片/职称/擅长/剩余号源），以便快速选择。
6. 作为患者，我想选定医生与时段并完成挂号，号源实时扣减，以便锁定号源。

9. 作为患者，我想收到电子处方的通俗语言解读，以便理解用药方法。
10. 作为患者，我想上传检查报告图片获得通俗解读，以便看懂指标。
11. 作为患者，我想所有 AI 产出都带"仅供参考，不替代医生诊断"免责声明标注，以便明确边界。

## Implementation Decisions

- **三端双栈后端**：支付宝小程序 C 端（原生 + antd-mini，ADR-0008，替代微信端 ADR-0002）、React + Umi + Ant Design B 端（ADR-0009）、Java 业务后端 server-java（Spring Boot + MyBatis-Plus）+ Python Agent 层 server-py（FastAPI + LangGraph，ADR-0009），均全部 AI 生成代码。
- **演示运行拓扑**：开发数据库部署于云服务器，团队通过账号密码直连，云安全组仅放行团队固定公网 IP；server-java（Maven）、server-py（uvicorn）、B 端与小程序开发环境均在本地运行。云服务器不部署应用，Agent 未经明确授权不得 SSH 登录或执行远程维护；小程序以开发者工具模拟器为主，真机通过预览二维码 + 开发者工具真机调试代理访问本地 server-java，不要求 HTTPS 域名。
- **存储分工**：PostgreSQL 16 存全部业务实体 + pgvector 存知识块向量（ADR-0003）；Redis 承担号源计数与缓存；Neo4j 只存医学知识图谱（症状/疾病/科室/药品/禁忌五类节点 + 边），不装业务实体、无任何双写（ADR-0006）。
- **LLM**：火山方舟一个 key；对话/视觉解读用 `doubao-seed-2.1-turbo`，RAG 向量化用 `doubao-embedding-vision`；C 端对话三档可选（自动/快速回答/深度思考），默认自动——自动档按场景分配（普通对话/导诊关闭思考，报告解读走高档），快速始终关闭思考，深度始终走高档（ADR-0015）。
- **Agent**：LangChain + LangGraph 编排（ADR-0005），依赖版本锁死；tool 函数为薄壳（仅参数校验），业务逻辑全在 service 层。第一版工具：`search_knowledge`（pgvector 召回）、`traverse_graph`（Neo4j 一跳扩展）、`recommend_doctors`、`get_doctor_slots`、`create_appointment`、`get_appointment`。C 端 Agent 只做通用药品知识解释，不做个性化用药决策；禁忌检查仅保留在 B 端医生开方流程（ADR-0016）。
- **领域实体**：patients（C 端 mock 登录身份）、health_profiles（同一患者账号 1:N，基础信息 + 过敏史）、staff_users（医生/管理员，独立账号体系）、hospitals、departments、doctors、schedules（total_slots/remaining_slots，号源池计数 ADR-0007）、appointments（分配序号 + 状态：已约/已取消/已接诊）、condition_summaries、consultation_records（医生填写的诊断结论 + 医嘱）、prescriptions + prescription_items（审核状态流转）、medications（药品业务信息唯一权威来源）、report_interpretations、knowledge_chunks、agent_call_logs、in_app_messages（站内消息通道，票 09 首建）、med_checkin_records（服药打卡/提醒记录）；禁忌与药品相互作用关系唯一来源为 Neo4j 图谱（见 ADR-0006）。
- **API 契约概略**：`/api/c/*`（会话、导诊对话 SSE、推荐卡片、挂号、挂号单管理、处方解读、报告解读、档案时间线）；`/api/b/*`（登录、机构/科室/医生/排班 CRUD、接诊台、电子处方与审核、图谱数据、看板统计、Agent 日志、演示重置）。
- **关键交互**：结构化消息卡片（小程序聊天区自定义消息类型）；工具调用可视化（LangGraph 事件流 -> SSE -> 小程序进度条 + B 端日志页）；语音输入用 `my.getRecorderManager` 录音 -> 火山引擎语音识别 -> 文本进对话，TTS 播报同源（火山引擎，ADR-0008）；情绪标签经 LLM 结构化输出的 emotion 字段驱动 UI 变色与安抚文案；情感化人设集中在 system prompt。
- **硬约束**：免责声明标注为全局 UI 组件 + 后端统一注入，覆盖导诊建议、病情摘要、处方解读、报告解读、拍照分析、就诊小结、LLM 生成的用药解释与替代建议等一切 AI 产出，无例外。
- **Mock 边界**：支付宝登录维持 mock；购药与收费的业务实体（药品订单、挂号收费记录、库存）按 ADR-0012 为真实后端实体，支付动作为模拟状态机（不接支付网关），Mock 支付仍需具备点击后展示成功态的可演示反馈。
- **施工纪律**：顺序 P0（导诊挂号主闭环 + B 端基础管理）-> P1（电子处方 + RAG + 禁忌 + 报告解读）-> P2（图谱可视化 + 情感化）-> 档外功能；每个功能可插拔；演示主线只依赖 P0+P1；支线亮点（含图谱可视化）按完成情况插拔。

## Testing Decisions

- **server-java 主 seam**：HTTP API 层使用 MockMvc 测外部行为；规则引擎单测覆盖危险输入触发和正常输入不误触。
- **server-py 主 seam**：Agent HTTP 接口使用 TestClient；LLM 与业务回调均以 fake 替换，断言工具调用顺序和回调参数，不直接写业务库。
- **防超卖**：API 层并发测试--N 并发抢最后 1 个号源，恰好 1 个成功，Redis 与 PG 计数一致。
- **禁忌规则**：service 层单元测试（过敏史 × 药品 -> 拦截/放行）。
- **前端（两端）**：不写自动化测试，以演示剧本手动验收--两周周期的现实取舍。
- 集成测试在本地运行，通过 `TEST_DATABASE_URL` / `TEST_REDIS_URL` / `TEST_NEO4J_URI` 连接云端独立测试库，不得复用演示数据；测试失败不得触发 SSH、远程部署或云端服务变更。

## Out of Scope

- 实时医患 IM/视频问诊、支付、随访计划真实执行、商保快赔、家庭账户（跨账号成员与授权体系）、慢病管理计划；同一患者账号下为本人/家人创建并切换多份健康档案属于范围内能力，不等同于家庭账户。
- 微服务拆分、异地多活、隐私计算（仅设计文档叙述，属 D 方向）。
- 端到端实时语音对话（RTC）、订阅消息真推送。
- 小程序上架与审核。

## Further Notes

- **演示剧本**：主线（症状 -> 情感化追问 -> 推荐 -> 挂号 -> 切 B 端接诊台看摘要 -> 开方 -> 回 C 端处方解读）；支线亮点（图谱可视化、过敏禁忌拦截、并发防超卖）。
- **Seed 规模**：2 医院、6–8 科室、15–20 医生、未来 7 天排班、15–20 症状场景图谱数据、30–50 药品 + 禁忌规则、演示账号（患者 2 / 医生 2 / 管理员 1）。
- 术语以根目录 `CONTEXT.md` 为准；架构决策见 `docs/adr/0001`–`0022`。

# 药品管理、药品订单与挂号收费（Spec 0002）

Status: ready-for-agent
日期： 2026-07-31 · 依据：ADR-0012（实体真实、支付 Mock）、CONTEXT.md 术语"药品订单""挂号收费"

## Problem Statement

当前 demo 缺三块业务能力：药品只作为开方时的下拉选项存在，无价格、无库存、无 B 端管理面；患者拿到审核通过的电子处方后，购药入口是纯前端 Mock（点击弹 toast，不落库、无订单实体），"售卖模块"名不副实；挂号全程不涉及任何费用，与真实就医流程不符。这三块缺失导致 B 端无可演示的药品/订单/收费管理面，C 端购药与挂号收费无法形成业务闭环。

## Solution

按 ADR-0012 的"业务实体真实、支付 Mock"边界，新增三个模块：药品管理（medications 增价格库存字段 + B 端只读编辑管理面）、药品订单（处方驱动购药，真实订单实体 + 预扣库存 + 模拟支付状态机）、挂号收费（挂号即产生诊查费记录，金额挂医生职称，模拟支付状态机）。三个模块后端实体进 PostgreSQL 由 server-java 唯一写入，支付动作为一键模拟状态机不接网关，B 端各有独立管理页，C 端购药与挂号收费形成可演示闭环。

## User Stories

**药品管理**

52. 作为管理员，我想在 B 端药品管理页查看药品列表（名称/通用名/规格/价格/库存/状态），以便掌握药品资产。
53. 作为管理员，我想编辑药品的价格与库存，以便调价与补库存。

## Implementation Decisions

- **架构边界（ADR-0012）**：药品订单、挂号收费记录、药品库存为真实业务实体进 PostgreSQL，由 server-java 唯一写入并纳入审计；支付动作为模拟状态机（UNPAID -> PAID），不接任何支付网关、不接收真实回调。ADR-0008 原"购药/支付维持 mock 边界"已细化为"支付链路 mock、业务实体真实"。
- **支付基础设施解耦**：药品订单的支付状态内嵌在订单状态机中（UNPAID/PAID/DONE/CANCELLED），不进 payments 表；挂号收费独立用 payments 表（关联 appointment_id，UNPAID/PAID）。两者各自有独立的模拟支付接口与状态机，互不共享、互不阻塞，可并行实施。
- **Schema 演进（drop + recreate + seed，不用迁移工具）**：
  - medications 增 `price DECIMAL(10,2)` + `stock INT`（库存为业务字段，与号源同属 PG 业务实体，不进 Neo4j，ADR-0006 边界不变）；seed 补齐 30 条药品的价格与库存。
  - doctors 增 `registration_fee DECIMAL(10,2)`，seed 按职称定价（主任医师 50 / 副主任医师 30 / 主治医师 20）。
  - appointments 增 `registration_fee DECIMAL(10,2)`，挂号时从 doctors 快照写入。
  - 新增 `drug_orders` 表（id, patient_id, prescription_id, status default 'UNPAID', total_amount, created_at, paid_at, cancelled_at；status CHECK IN ('UNPAID','PAID','DONE','CANCELLED')）。
  - 新增 `drug_order_items` 表（id, drug_order_id FK cascade, medication_id FK, quantity, unit_price, subtotal）。
  - 新增 `payments` 表（id, appointment_id FK unique, amount, status default 'UNPAID', created_at, paid_at；status CHECK IN ('UNPAID','PAID')），只承载挂号收费。
- **药品管理 CRUD 范围**：只读 + 编辑（改价格/库存/上下架 is_active），不新增不删除。理由：新增药品会破坏 Neo4j 禁忌子图按 medication_id 的对齐（ADR-0006），删除药品会破坏 prescription_items 外键引用与历史处方完整性。上下架控制开方选药可见性。
- **药品订单触发点（处方驱动）**：订单明细复用 APPROVED 处方的 prescription_items（药品 + 数量，数量默认 1 可改）；订单与 prescription_id 强关联。购药入口在 C 端处方详情页，替换现有纯前端 Mock 按钮。
- **药品订单状态机**：`UNPAID -> PAID -> DONE`，未支付订单可 `CANCELLED`。无 SHIPPED 发货态（mock 物流号无演示价值）。DONE 由 B 端人工"确认完成"或 PAID 后系统标记。状态常量进 `contracts/order-flow.json`，双栈只读消费。
- **药品库存扣减（预扣模型）**：下单时扣减 medications.stock，取消未支付订单时回补。采用 PostgreSQL 行锁 + 条件更新（`UPDATE medications SET stock = stock - n WHERE id = ? AND stock >= n`，affected rows = 0 即库存不足下单失败），禁止先查后改。不引入 Redis 计数--药品购药并发度远低于抢号场景，PG 行锁足以防超卖，避免过度设计（与号源 ADR-0007/0011 的 Redis+PG 双写不同）。
- **挂号收费金额来源**：挂医生职称。doctors.registration_fee 为定价基准（B 端医生管理页可编辑）；挂号时快照写入 appointments.registration_fee，不受后续调价影响。
- **挂号收费时机（挂号即欠费）**：挂号成功（号源扣减 + 挂号单写入事务内）即产生 UNPAID 收费记录，不阻塞号源扣减，保持现有 AppointmentService.create() 事务结构不动；收费记录作为挂号单附属。收费状态机极简 `UNPAID -> PAID`，无退款态（取消挂号不触发退款，demo 容忍）。状态常量进 `contracts/payment-flow.json`。
- **跨栈契约（新增 contracts/，ADR-0010 单一事实源）**：
  - `contracts/order-flow.json`：statuses（unpaid/paid/done/cancelled）、status_labels、decisions（pay/cancel/complete）、message_types、messages，格式参照 prescription-flow.json。
  - `contracts/payment-flow.json`：statuses（unpaid/paid）、status_labels、decisions（pay）、messages，格式参照 contraindication.json。
  - 状态、决定、消息类型及其 TS 类型均从 contracts/ 推导，双栈只读消费，禁止端内私写。
- **B 端新增页面（routes.ts 追加 + controller/b/ 三件套）**：
  - 药品管理 `Medication/`（`/api/b/medications`）：列表 + 编辑价格/库存/上下架。
  - 药品订单管理 `DrugOrder/`（`/api/b/drug-orders`）：按状态筛 + 明细 + 取消/确认完成。
  - 收费管理 `Payment/`（`/api/b/payments`）：按状态筛 + 明细 + 模拟支付。
  - 医生管理页 `Doctor/` 表单增"挂号费"字段编辑（归入挂号收费，不单独成页）。
  - 新增路径需加入 `admin/src/app.tsx` 的 ADMIN_PATHS 限制 doctor 角色禁入。
- **C 端改造**：
  - 新增"我的药品订单"页并在 app.json 注册；购药入口由 prescriptions 页 mock order() 替换为真实 `/api/c/drug-orders` 下单调用（POST，传 prescription_id + 数量）。
  - 挂号卡片（AppointmentCardBase / AppointmentOut / Agent AppointmentCard 三处 record）增 registration_fee 字段；appointments 页卡片增费用与支付状态展示行；新增挂号收费模拟支付调用 `/api/c/appointments/{id}/payment/pay`。
- **分层归属**：server-java 新代码进入既有分层--controller/b/（MedicationController、DrugOrderController、PaymentController）、controller/c/（C 端订单与支付 controller）、service/、mapper/、entity/、config/（Contracts 加载新契约）；DTO 映射用 MapStruct；B 端新 CRUD 继承 MyBatis-Plus ServiceImpl。server-py 不参与（购药与收费为确定性业务流程，无 LLM 编排，不进 Agent 层）。
- **审计**：药品订单创建、状态流转、库存扣减回补、挂号收费记录创建与支付，统一在 server-java 入口审计；不记录患者敏感原文，只记录脱敏摘要、操作类型与结果。

## Testing Decisions

- **主 seam：server-java MockMvc HTTP 外部行为测试**（AGENTS.md 约定）。三个模块的核心行为均在 HTTP 层验证：
  - 药品管理：编辑价格/库存/上下架返回正确数据；停用药品不出现在开方选药列表。
  - 药品订单：处方驱动下单成功（库存扣减、订单创建、状态 UNPAID）；库存不足下单失败（负向）；取消未支付订单库存回补；模拟支付 UNPAID->PAID；确认完成 PAID->DONE。
  - 挂号收费：挂号成功产生 UNPAID 收费记录（金额 = 医生职称价）；模拟支付 UNPAID->PAID；appointments 返回费用与支付状态。
- **防超卖（药品库存）**：并发下单同一库存不足的药品，成功数不超过库存数（参照号源防超卖测试先例，但用 PG 行锁而非 Redis）。
- **契约消费**：测试断言使用 contracts/ 中的状态/决定常量，不硬编码字符串。
- **前端**：不写自动化测试，浏览器实测无控制台错误 + 人工走通"药品管理调价 -> C 端处方购药 -> B 端订单管理""挂号 -> 我的挂号看费用 -> 模拟支付 -> B 端收费管理"两条闭环。

## Out of Scope

- 接入真实支付网关（支付宝/微信支付沙箱）、支付回调幂等、对账（ADR-0012 明确排除）。
- 药品新增/删除（破坏 Neo4j 禁忌子图对齐与历史处方完整性，4a 决策排除）。
- 药品订单发货/物流（SHIPPED 态，2b 决策排除）。
- 挂号退款的完整流程（3c 决策排除，取消挂号不触发退款）。
- 自由选购药品（无处方购药，2a 决策排除，合规风险）。
- 药品订单的支付状态合并进 payments 表（问题 5 决策排除，两者解耦）。

## Further Notes

- 药品库存与号源是两套独立的防超卖机制：号源用 Redis 原子 DECR + PG 对账（ADR-0007/0011，高并发抢号），药品库存用 PG 行锁条件更新（低并发购药），不要混用。
- 挂号收费不改动现有 SlotAccounting 号源扣减逻辑，收费记录作为挂号单的附属在挂号事务后写入（收费记录写入失败不回滚挂号，与病情摘要同模式）。
- 演示叙事：开方 -> 审核 -> C 端购药 -> B 端订单管理（一条线）；挂号 -> 看费用 -> 模拟支付 -> B 端收费管理（另一条线），两条线独立可并行演示。

# 在线问诊、处方审核与购药闭环（Spec 0003）

Status: 票 55 主闭环已施工（2026-08-07，分支 t54-online-consultation-loop，待人工端到端验收后置 done）；票 56 ready-for-agent
日期：2026-08-07 · 依据：CONTEXT.md 术语“预问诊 / 预问诊模式 / 在线问诊 / 在线问诊单 / 在线问诊进度 / 科室待接诊池 / 在线问诊交流 / 电子处方”及《在线问诊医生分配模式调研》

## Problem Statement

当前 C 端把“在线问诊”当作普通 Agent 会话处理：患者点击或输入在线问诊后，仍只看到 Agent 对症状追问，既没有专用流程、病情摘要确认，也没有真人医生接入状态。与此同时，现有 B 端接诊台只消费挂号单，病情摘要、接诊记录和电子处方全部依附线下挂号，导致在线问诊与预约挂号在产品语义、业务实体和演示路径上无法区分。

患者无法判断当前是在与 AI 预问诊还是已经连接医生，医生无法从独立的在线问诊队列接诊，评审也无法看到题目要求的“Agent 预问诊 → 医生发起图文/视频问诊 → 开方 → 审核 → 购药”跨端闭环。若继续复用挂号单承载在线问诊，还会错误占用线下排班与号源，并把两种服务的状态、收费和接诊语义进一步耦合。

## Solution

新增一条与线下挂号完全独立的在线问诊主流程。患者从明确入口进入预问诊模式，系统锁定当前健康档案，Agent 通过自然对话持续整理可修改的结构化病情摘要；患者确认摘要后，系统创建不绑定医生、不占线下号源的在线问诊单，并按建议标准科室投入平台级科室待接诊池。符合科室资格的 B 端医生查看摘要并明确接受后，系统原子绑定医生，C 端进入医生问诊中。

图文问诊采用 server-java 持久化、C/B 端轮询的双向文字消息；视频问诊只模拟连接界面与状态，不传输真实音视频。医生填写诊断结论、医嘱并可开具电子处方，然后独立完成问诊。处方沿用现有禁忌检查和管理员审核状态机，问诊完成不等待审核；只有审核通过的处方才对 C 端可见并进入处方解读、购药、模拟支付、履约完成及服药提醒链路。

## User Stories

**C 端：入口、服务对象与预问诊**

1. 作为患者，我想从独立的“在线问诊”入口进入服务，以便不会把在线问诊误认为智能导诊或预约挂号。
2. 作为患者，我想进入在线问诊后看到“AI 预问诊”状态，以便知道当前尚未连接真人医生。
3. 作为患者，我想在没有激活健康档案时被引导创建或选择档案，以便本次问诊有明确服务对象。
4. 作为为家人就医的患者，我想在预问诊开始时锁定所选健康档案，以便后续切换档案不会改变本次问诊对象。
5. 作为患者，我想由 Agent 一次只追问一个最关键问题，以便自然补充症状而不是填写冗长表单。
6. 作为患者，我想 Agent 整理主诉、现病史和过敏史，以便医生接诊前快速理解病情。
7. 作为患者，我想 Agent 在理解病情时读取本次锁定档案的可信信息，以便减少重复输入。
8. 作为患者，我想继续与 Agent 对话补充或纠正信息，以便病情摘要随新信息更新。
9. 作为患者，我想摘要只展示病情内容，不混入医生列表或医生选择，以便专注核对信息准确性。
10. 作为患者，我想明确点击确认摘要，以便系统不会在我尚未认可内容时提交给医生。
11. 作为患者，我想所有 Agent 回复与病情摘要都显示“仅供参考，不替代医生诊断”，以便明确 AI 能力边界。
12. 作为患者，我想危险症状在 server-java 确定性规则命中时优先收到紧急就医提醒，以便在线问诊不会延误急症处理。
13. 作为患者，我想普通 AI 会话中的症状描述不会静默创建在线问诊单，以便业务副作用始终由明确入口和确认动作触发。

**C 端：端到端进度与等待接诊**

14. 作为患者，我想看到固定的“AI 预问诊 → 患者确认摘要 → 等待医生接诊 → 医生问诊中 → 问诊已完成”进度，以便知道整个跨端流程所处位置。
15. 作为患者，我不想看到主诉、病史等内部字段完成百分比，以便界面只呈现有业务意义的进度。
16. 作为患者，我想确认摘要后直接进入等待医生接诊，以便不必在摘要页额外挑选医生。
17. 作为患者，我想系统根据建议标准科室寻找医生，以便在不知道应该找谁时也能得到真人服务。
18. 作为患者，我想等待页说明正在匹配哪个标准科室的医生，以便了解匹配依据。
19. 作为患者，我想医生尚未接受时不显示“已匹配成功”，以便不会误以为真人医生已经参与。
20. 作为患者，我想等待期间主动取消问诊，以便不再需要服务时可以结束等待。
21. 作为患者，我想等待超过默认 10 分钟后得到明确失效提示，以便不会无限等待。
22. 作为患者，我想取消或失效后复用原病情摘要重新提交，以便无需重新完成预问诊。
23. 作为患者，我想重复点击确认摘要时返回原有进行中问诊，而不是创建多张问诊单，以便避免重复接诊。
24. 作为患者，我想同一健康档案同时最多有一条等待或进行中的在线问诊，以便不会被多个医生并行接诊并产生上下文混乱。
25. 作为管理多份健康档案的患者，我想不同档案可以分别发起在线问诊，以便为不同家庭成员获得服务。
26. 作为患者，我想医生接受后立即看到医生姓名、职称、医院和科室，以便确认真人接诊身份。

**C 端与 B 端医生：图文/视频问诊**

27. 作为患者，我想在医生接受后进入独立的医生问诊页面，以便不把医生消息与 Agent 会话混淆。
28. 作为患者，我想在图文问诊中发送文字并轮询看到医生回复，以便完成可演示的双向交流。
29. 作为医生，我想在图文问诊中发送文字并看到患者回复，以便根据补充信息继续诊疗。

## Implementation Decisions

- **独立领域模块**：新增预问诊模块、在线问诊模块和在线问诊交流模块。在线问诊状态、科室路由、医生接受、取消、失效、交流权限与完成行为由 server-java 的在线问诊模块统一承担；不得把逻辑加入挂号模块，也不得用可空排班或虚假挂号单承载在线问诊。
- **主 interface 与 seam**：在线问诊模块向 C/B 端分别提供少量高层操作——开始或恢复预问诊、确认摘要并提交、查询本人问诊、取消；查询科室池、接受、读取详情、发起交流、发送消息、完成。状态校验、身份派生、超时处理和并发控制全部隐藏在模块实现内，调用方不得自行拼装状态流转。
- **预问诊草稿**：新增预问诊草稿实体，归属 patient_id，绑定进入时的 health_profile_id 与 conversation_id，保存结构化摘要快照、建议标准科室和草稿状态。会话继续保持患者账号级、不绑定健康档案；健康档案锁定关系只存在于预问诊草稿，避免破坏既有会话领域定义。
- **预问诊草稿状态**：草稿区分收集中、待确认和已提交。患者继续与 Agent 对话时更新摘要快照并回到待确认；只有患者明确确认后才将草稿提交并创建在线问诊单。已提交草稿不可再次创建新单，只返回关联结果。
- **病情摘要结构**：摘要至少包含主诉、现病史和过敏史，并保留统一免责声明标注。摘要是 Agent 产出的结构化参考信息，不是病历或诊断报告；患者补充信息后应生成新快照，生成失败不得丢失已持久化的对话或上一版摘要。
- **可信预问诊模式**：C 端请求携带预问诊草稿标识，server-java 校验患者归属、草稿状态和锁定健康档案后，强制以 preconsultation 场景调用 server-py；不得信任客户端任意指定场景来获得业务权限。
- **Agent 场景隔离**：共享对话契约新增 preconsultation 场景，server-py 为该场景选择专用提示词与工具集。预问诊允许医学知识检索和受控标准科室解析，但不暴露医生推荐、号源查询、创建挂号或查询挂号工具，避免预问诊误入挂号闭环。
- **一次一问与摘要更新**：预问诊 Agent 每轮只提出一个最关键的补充问题；每个成功轮次结束后，以非流式结构化调用更新摘要快照。结构化调用使用 fake 可替换 seam，失败时保留上一版摘要并允许继续对话。
- **标准科室解析**：创建在线问诊单前，建议标准科室必须从平台标准科室目录中受控解析，返回值须经 server-java 校验为现有标准科室 ID；不得让 LLM 自由生成科室 ID 或医院实际科室 ID。尚不能收敛到单一标准科室时不得建单，应继续预问诊。
- **在线问诊单**：新增在线问诊实体，保存 patient_id、锁定 health_profile_id、来源预问诊草稿、conversation_id、standard_department_id、可空 doctor_id、结构化病情摘要、状态、接诊方式、expires_at、accepted_at、completed_at、cancelled_at 与创建更新时间。conversation_id 删除时置空，业务实体与临床记录保留。
- **在线问诊状态机**：正常路径为 WAITING_DOCTOR → IN_PROGRESS → COMPLETED；WAITING_DOCTOR 可转 CANCELLED 或 EXPIRED。COMPLETED、CANCELLED、EXPIRED 为终态。默认接诊截止时间为创建后 10 分钟，超时值由共享契约或配置读取，不在端内散落硬编码。
- **单一进行中约束**：数据库以 health_profile_id 的条件唯一约束保证每份档案最多一条 WAITING_DOCTOR 或 IN_PROGRESS 问诊；重复提交使用患者与预问诊草稿幂等键返回原问诊单，不依赖前端按钮禁用。
- **失效处理**：列表、详情和接受操作进入模块时都先收敛已过 expires_at 的 WAITING_DOCTOR 为 EXPIRED；不为 demo 引入分布式任务调度。患者可从 CANCELLED 或 EXPIRED 问诊复用原摘要生成新的待接诊问诊单。
- **科室待接诊池**：池按 standard_department_id 在平台范围查询，不使用城市、医院、院区、线下排班或号源条件。可见医生必须拥有 doctor 角色 B 端账号，且其实际科室映射到同一标准科室；当前范围不新增在线服务开关或在线排班。
- **原子接受**：接受问诊使用带预期状态、空 doctor_id 与未过期条件的单条条件更新，并在同一事务内绑定医生和写 accepted_at。并发请求中只有 affected rows 为 1 的医生成功，其余返回冲突；跨科室医生在进入更新前即被拒绝。
- **跨端进度**：C 端固定展示五步进度，前两步来自预问诊草稿，后三步来自在线问诊单。预问诊内部字段完整度不对用户展示。等待页以短轮询查询状态，医生接受后返回可信医生身份；不为本功能扩展现有对话 WebSocket。
- **在线问诊交流**：新增独立医患消息实体，关联在线问诊单，发送者类型限定 PATIENT、DOCTOR、SYSTEM。只有已绑定患者和医生可读写；只在 IN_PROGRESS 状态允许发送，完成后只读。消息内容不得写入审计日志或 Agent trace，也不得存入 Agent conversations/messages 表。
- **图文问诊**：C/B 端分别通过 server-java 接口发送和轮询文字消息，消息按单调 ID 或创建时间增量读取。该能力是持久化轮询交流，不宣称实时 IM，不复用 Agent SSE 轮次。
- **模拟视频**：医生发起视频时持久化 VIDEO 接诊方式与模拟开始时间，C 端展示医生身份、连接状态和计时；不采集摄像头、麦克风，不建立 WebRTC、信令或媒体服务器。图文与视频都必须在医生接受后发起。
- **接诊记录**：医生完成在线问诊时保存诊断结论与医嘱，并将问诊单原子推进到 COMPLETED。完成操作幂等；完成后禁止继续发送医患消息。AI 生成的就诊小结仍需统一免责声明。
- **临床上下文模块**：为处方、禁忌检查、处方审核、患者处方列表、服药提醒和健康时间线提供统一的临床上下文解析 interface，根据线下挂号或在线问诊来源返回可信 patient_id、health_profile_id、doctor_id、来源类型与发生时间。调用方不直接编写两套身份分支。
- **接诊记录关联泛化**：接诊记录支持关联挂号单或在线问诊单，两个外键必须且只能存在一个，并分别保持一对一唯一约束。不得用无外键保障的 source_type/source_id 多态引用替代真实关系。
- **处方关联泛化**：电子处方支持关联挂号单或在线问诊单，两个外键必须且只能存在一个，并分别保持一对一唯一约束。线上线下处方共用同一状态、处方明细、管理员审核、解读和免责声明逻辑。
- **开方权限与安全**：在线问诊处方只能由已接受该问诊的医生在 IN_PROGRESS 阶段创建；患者与档案上下文从在线问诊单派生。预览检查和最终提交都复跑同一确定性禁忌规则，医学事实源不可用时继续 fail closed。
- **问诊与审核解耦**：医生提交处方后处方进入 PENDING，但可独立完成在线问诊。管理员 APPROVED 或 REJECTED 不改变在线问诊 COMPLETED 状态；只有 APPROVED 处方对 C 端可见并可购药。
- **审核与患者链路复用**：管理员审核队列新增来源类型和来源标识，但复用既有审核决定、通俗处方解读与统一免责声明。患者处方列表、药品订单归属校验、库存预扣、模拟支付、订单完成、服药提醒和时间线必须同时支持两种处方来源。
- **无在线问诊收费**：在线问诊单不进入挂号收费表，不创建任何问诊支付记录，不阻塞入池或接诊。药品订单仍沿用真实订单实体与模拟支付状态机。
- **共享契约**：新增在线问诊流程契约，集中定义问诊状态、状态标签、决定、进度步骤、接诊方式、消息发送者类型、默认超时与用户文案；预问诊摘要字段和草稿状态同样由共享契约定义。聊天场景与知识源默认映射扩展 preconsultation，Java、Python 和 TypeScript 均从 contracts 推导。
- **C 端页面边界**：在线问诊作为首页就医服务的独立入口，使用专用预问诊、摘要确认、等待接诊和医生问诊页面。Agent 气泡与医生气泡在页面、身份标识和数据来源上明确分离；在线问诊不展示线下日期、号源、序号、院区或到院指引。
- **B 端页面边界**：医生接诊台增加独立的在线问诊区域，区分科室待接诊池、本人进行中和已完成记录。线下挂号队列保持原语义，不把两类记录合并为伪统一列表；管理员处方审核只在来源展示上扩展。
- **审计与隐私**：server-java 统一审计开始预问诊、确认摘要、建单、取消、接受、发起接诊、完成、开方、审核和购药等动作，只记录身份 ID、操作类型、参数类型、状态与结果；不得记录患者病情原文、摘要内容、医患消息或处方解读原文。
- **运行拓扑不变**：server-java 仍是唯一对外入口和业务写入方；server-py 只负责预问诊 Agent 编排、摘要结构化与既有处方解读，不直接写业务库。PostgreSQL 保存全部在线问诊业务实体，不引入新的中间件或云端应用部署。
- **Schema 管理**：所有新表、列、约束、索引和 seed 按项目约定更新 schema.sql 与幂等 seed，开发期 drop + recreate + seed，不引入迁移工具。测试配置同步维护且不得加载 .env。
- **后续实施边界**：本规格后续仅拆为两张票。第一票完成在线问诊主闭环（预问诊、摘要确认、待接诊池、接受、交流、模拟视频、诊断医嘱、完成）；第二票在第一票完成后泛化接诊记录与处方来源，并接通审核、购药、支付、履约、提醒和时间线。

### 实施回写（票 55，2026-08-07）

- **诊断与医嘱的落点**：主闭环把诊断结论与医嘱直接持久化在在线问诊单（`online_consultations.diagnosis/advice`）上，完成动作幂等；“接诊记录关联泛化（双外键二选一）”仍归票 56，届时再迁移为独立接诊记录。
- **并发接受 seam 的落地形态**：默认测试套件以内存并发测试（仿 `AppointmentConcurrencyTest`）覆盖两医生竞争语义；真实 PostgreSQL 集成测试 `OnlineConsultationPgIntegrationTest` 以 `-Dpg.it=true` 显式开启，指向一次性库（云端 `zhiyu_it`），覆盖条件更新 affected-rows、部分唯一索引与惰性失效，不以真实等待验证 10 分钟超时，fixtures 用 9900xx 号段且跑后清场。
- **契约落地**：`contracts/online-consultation.json` 集中定义问诊状态机、草稿状态、五步进度、接诊方式、发送者类型、600 秒超时、摘要字段与文案；`chat-defaults.json`/`knowledge.json` 登记 preconsultation 场景；`chat-realtime.json` 的 `chat_optional_fields` 增加 `preconsultation_draft_id`；摘要快照经 SSE `message` 事件 payload 的 `preconsultation_summary` 字段回传（不新增事件类型）。
- **预问诊会话归属**：草稿绑定 conversation_id 且 `ON DELETE SET NULL`，会话继续保持患者账号级不绑档案；档案锁定关系只存在于草稿。
- **B 端落点**：在线问诊区域以 Tabs 并入医生接诊台（线下接诊/在线问诊分区，不做伪统一列表），消息与池轮询为本仓库首批 setInterval 场景，卸载即清理。

## Testing Decisions

- **测试原则**：只验证模块 interface 可观察到的行为，不断言 controller、service、mapper 或 Agent 编排内部调用细节。状态机、身份约束、幂等、并发和持久化结果通过最高可用 seam 验证；内部重构不应迫使行为测试改写。
- **server-java 主 seam**：使用 MockMvc 覆盖 C/B 端 HTTP 外部行为，沿真实业务模块验证预问诊开始与恢复、摘要确认、在线问诊创建与查询、取消、失效、科室池、医生接受、交流权限、完成、在线问诊开方、审核后患者可见与购药。
- **身份与负向 HTTP 行为**：覆盖无健康档案不可开始、他人草稿/问诊不可读写、跨科室医生不可见或接受、查看摘要不推进状态、未接受不能交流或开方、完成后不能发送、未通过处方不可见或购药、请求体伪造患者或医生身份无效。
- **医生并发接受 seam**：使用 PostgreSQL 集成测试并发提交两名同标准科室医生对同一 WAITING_DOCTOR 问诊单的接受请求，断言恰好一人成功、doctor_id 与 accepted_at 只写一次、另一请求返回冲突。测试方式参照既有号源并发与条件状态更新先例，但不使用 Redis。
- **幂等与唯一约束**：覆盖重复确认摘要返回同一问诊单、同一档案不能创建第二条进行中问诊、重复完成返回已有结果、重复审核只有一个决定生效、C 端断线或重试不会重复产生业务副作用。
- **超时 seam**：通过可控时钟或显式过期数据验证 WAITING_DOCTOR 在默认 10 分钟后收敛为 EXPIRED、医生不可再接受、患者可复用摘要重新提交；测试不得真实等待 10 分钟。
- **server-py 主 seam**：使用 TestClient 测 preconsultation 场景，LLM、摘要结构化器、知识检索和业务回调均用 fake。断言一次只追问一个关键问题、锁定档案上下文正确注入、摘要字段正确返回、失败保留上一版摘要。
- **Agent 工具隔离**：通过 server-py HTTP 行为断言 preconsultation 场景不存在医生推荐、号源查询、创建挂号和查询挂号工具；受控标准科室解析只能返回候选目录中的 ID。普通 triage 和 interpretation 场景回归保持原工具与知识源行为。
- **契约一致性**：Java、Python 与 TypeScript 契约消费测试断言在线问诊状态、决定、进度、接诊方式、发送者类型、超时和 preconsultation 场景均来自 contracts；数据库 CHECK、事件类型和前端类型必须覆盖契约全部取值且无端内私写枚举。
- **处方回归**：所有既有线下挂号开方、禁忌拦截、管理员审核、C 端处方列表、药品订单、服药提醒与健康时间线测试继续通过；新增相同行为的在线问诊来源用例，重点验证临床上下文解析不会串患者、档案或医生。
- **前端验收**：不新增前端自动化测试。支付宝开发者工具实测 C 端入口、档案锁定、预问诊、摘要调整、五步进度、图文轮询、模拟视频、处方与购药；浏览器实测医生池、并发冲突反馈、图文回复、完成、管理员审核与订单履约。两端必须无红色控制台错误。
- **完整演示验收**：人工一次走通“进入在线问诊 → 锁定健康档案 → Agent 预问诊 → 患者调整并确认摘要 → B 端医生接受 → 图文双向消息或模拟视频 → 医生诊断、医嘱与开方 → 问诊完成 → 管理员审核通过 → C 端处方解读 → 创建药品订单 → 模拟支付 → B 端确认完成”。仅编译通过或单端 API 冒烟不算验收。
- **免责声明验收**：预问诊 Agent 回复、病情摘要、处方解读和 AI 就诊小结的 server-py 生成出口、server-java 兜底出口及 C/B 展示均断言固定免责声明标注，无例外。

## Out of Scope

- 患者手动选择或指定在线问诊医生；复诊、名医服务未来使用独立“指定医生问诊”入口，不插入当前摘要确认页。
- 医生在线服务开关、在线问诊排班、在线服务价格和按医生定价。
- 在线问诊收费、问诊支付、未接诊退款、收费对账或真实支付网关；本规格只有药品订单模拟支付。
- 真实实时医患 IM、WebSocket 推送、离线推送、已读回执、输入中状态和消息撤回；本规格图文采用 REST 持久化与轮询。
- 真实视频、音频、WebRTC、信令、媒体服务器、摄像头或麦克风采集；视频仅模拟连接 UI 与状态。
- 多医生会诊、转诊、医生接受后的退诊、患者在 IN_PROGRESS 阶段取消，以及一份健康档案同时进行多次在线问诊。
- Agent 诊断、Agent 开方、C 端个性化用药决策；诊断、医嘱与处方只能由已接受问诊的真人医生产生。
- 把在线问诊接入线下排班、号源、挂号收费、院区选择或就诊指引卡。
- 新增药师角色；处方审核继续由现有 admin 承担。
- 新增分布式定时任务或调度中间件；等待失效在业务入口惰性收敛。
- 云端应用部署、远程命令、云端 Compose 变更或新增基础设施。

## Further Notes

- 市场调研显示主流产品同时存在“极速问诊”和“定向问诊”：前者为非定向派单/抢单，后者由患者指定医生。本规格选择前者，因为入口从症状和 Agent 预问诊出发，且已确认患者不在摘要页选择医生。
- “自动匹配”在本规格中指把问诊单路由到合格医生集合，不是由系统立即随机绑定一名医生。医生必须在 B 端明确接受，接受前 C 端只能显示等待状态。
- 在线问诊进度与处方审核是两条独立状态线。医生完成问诊后患者可查看诊断与医嘱；处方仍可处于 PENDING，只有 APPROVED 后才对患者可见并允许购药。
- 第一张后续票形成可独立演示的在线问诊闭环，第二张票被第一张阻塞并形成处方审核与购药闭环；不得按前端、server-java、server-py 横向拆票，以免每张票都无法独立验收。
- 本规格涉及“在线问诊独立于挂号、非定向科室池由医生主动接受”的高成本业务决策，后续应单独形成 ADR，记录为何没有复用挂号单或默认采用患者选医生模式。
