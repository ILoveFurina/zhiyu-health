## 1. 背景介绍

### 1.1 业务背景

患者出现不适后，通常需要先自行判断科室，再分别查找医院、医生、出诊时间和剩余号源。科室名称与医生职称并不能直接回答“哪位医生擅长处理我的问题”，患者容易选错或反复搜索。挂号完成后，导诊过程中描述的症状也很难直接传递给医生，患者到诊室仍需重复陈述。

医生接诊前通常缺少患者主诉、症状时长、过敏史等结构化信息，接诊准备不足；开具处方时，还需要快速找到有效药品并核对禁忌。患者拿到处方和检查报告后，又可能因医学术语难以理解而无法正确执行医嘱。

本项目新建一个 B+C 联动的医疗健康平台：

- C 端支付宝原生小程序面向患者，以医疗 AI Agent 串联导诊、医生推荐、挂号、报告解读和处方解读。
- B 端管理后台面向医生与管理员，维护医院、科室、医生擅长、排班和药品目录，完成接诊、开方及处方审核。
- 主业务闭环为“资源配置 → 症状描述 → 智能导诊 → 医生推荐 → 挂号 → 医生接诊 → 开方 → 审核 → 患者查看与解读”。
- 红线症状、过敏禁忌和号源扣减属于确定性业务规则，不由 LLM 自由判断。

产品目标如下：

| 产品目标 | 成功判定 |
|---|---|
| 降低患者选科室和医生的理解成本 | 患者描述症状后获得包含推荐理由、擅长病症和真实号源的医生卡片 |
| 减少挂号与接诊之间的信息断点 | 挂号后自动生成病情摘要，C 端和医生接诊台展示同一挂号单及状态 |
| 打通接诊到处方解读 | 医生开方、管理员审核、患者查看及解读按业务状态连续完成 |
| 守住医疗安全边界 | 红线症状与用药禁忌由确定性规则处理，所有 AI 产出带免责声明标注 |
| 支持稳定现场演示 | 固定虚构数据可反复跑通主闭环，关键异常均有明确反馈和一致性结果 |

## 2. 产品概述

### 2.1 产品逻辑

核心业务流程：

    管理员维护医院、科室、医生擅长、排班和药品目录
      → 患者描述症状
      → server-java 先执行红线症状规则
        → 命中：中断普通导诊并提示尽快就医或拨打 120
        → 未命中：Agent 追问并推荐科室、医生和真实号源
      → 患者选择医生与时段完成挂号
      → 系统扣减号源、创建挂号单并生成病情摘要
      → 医生在 B 端查看摘要并完成接诊
      → 医生从启用药品目录开具电子处方
      → server-java 执行过敏与相互作用规则
      → 管理员审核处方
        → 驳回：医生修改后重新提交
        → 通过：患者收到处方并查看通俗解读

跨模块关联原则：

- B 端基础数据决定 C 端可推荐的医院、科室、医生、擅长病症和号源。
- C 端挂号产生的挂号单和病情摘要直接进入对应医生的接诊台。
- 医生开方只能使用 B 端已启用药品；管理员审核结果同步给医生和患者。
- C 端和 B 端读取同一业务实体，不得用两套静态数据模拟联动。

### 2.2 信息架构

| 端 | 一级模块 | 二级页面或能力 | 与其他模块的关系 |
|---|---|---|---|
| C 端 | AI 诊室 | 会话、语音输入、导诊追问、医生推荐、挂号卡片 | 读取健康档案、医生擅长、排班和号源；生成挂号单与病情摘要 |
| C 端 | 就医服务 | 我的挂号、取消挂号、就诊指引 | 与 B 端接诊台共享挂号单和状态 |
| C 端 | 健康档案 | 本人/家人档案、过敏史、健康时间线、服药打卡 | 为禁忌判断和个性化解读提供当前服务对象 |
| C 端 | 健康解读 | 电子处方、报告、药盒、皮肤、饮食、舌苔解读 | 处方来自 B 端审核结果，其他解读形成独立记录 |
| B 端 | 基础资料 | 医院、科室、医生及擅长病症、药品目录 | 支撑推荐、排班、开方和展示 |
| B 端 | 号源管理 | 医生排班、号源发布与停诊 | 向 C 端提供可预约时段和剩余号源 |
| B 端 | 医生工作台 | 今日排班、接诊台、病情摘要、诊断与开方 | 承接 C 端挂号和病情摘要 |
| B 端 | 处方审核 | 待审核、通过、驳回 | 审核结果同步医生与患者 |
| B 端 | 运营与审计 | 数据看板、Agent 日志、知识图谱、演示重置 | 支撑运营查看、安全审计和现场演示 |

### 2.3 角色术语

| 角色/术语 | 定义 | 场景说明 |
|---|---|---|
| 患者 | 使用支付宝小程序的就医服务对象 | 描述症状、选择医生、挂号、查看处方和健康记录 |
| 医生 | 使用 B 端工作台的出诊人员 | 查看本人挂号患者、病情摘要，完成接诊和开方 |
| 管理员 | 医院运营管理者，本项目中兼具药师审核职能 | 维护基础数据、发布排班、审核处方、查看运营数据 |
| C 端 | 面向患者的支付宝原生小程序 | 承载医疗 AI Agent 和患者业务页面 |
| B 端 | 面向医生与管理员的 React 管理后台 | 承载资料管理、接诊、处方审核和运营页面 |
| 智能导诊 | 症状描述、必要追问、科室推荐、医生推荐和挂号的连续流程 | Agent 只做导诊与预问诊，不作医学诊断 |
| 病情摘要 | Agent 根据本次导诊整理的结构化患者主诉 | 挂号后供对应医生接诊前查看，不等同于病历或诊断 |
| 健康档案 | 患者账号下本人或家人的健康数据集合 | 当前激活档案用于过敏禁忌和个性化解读 |
| 号源 | 某医生某排班时段内可预约的数量 | 挂号扣减，取消返还，必须防超卖 |
| 挂号单 | 患者对某一医生排班的预约记录 | 状态为已约、已取消或已接诊 |
| 电子处方 | 医生接诊后开具并交由管理员审核的药品清单 | 审核通过后患者才能作为有效处方查看 |
| 免责声明标注 | 固定文案“仅供参考，不替代医生诊断” | 所有 AI 生成或改写内容必须显示 |

> 本项目“前台”指 C 端支付宝小程序。以下说明定义功能与交互，页面布局可由 UED 调整。

#### 3.2.1 AI 诊室页面

页面功能概述：患者通过自然语言完成智能导诊，并在会话内获得医生推荐、选择号源和完成挂号。

| 模块 | 需求说明 | 图示 |
|---|---|---|
| 顶部区域 | 展示当前健康档案、AI 思考档位和对话记录入口；未建档时显示建档引导 | 待补充 |
| 消息区域 | 展示患者消息、AI 回复、工具工作状态、风险提示和结构化卡片 | 待补充 |
| 快捷入口 | 展示 AI 诊室、找医院、看报告、拍药盒、拍皮肤、拍饮食、拍舌苔 | 待补充 |
| 输入区域 | 支持文字输入、录音转文字、发送、停止生成和 TTS 播放 | 待补充 |
| 推荐卡片 | 展示医生照片、医院、科室、职称、擅长病症、推荐理由、时段和余号 | 待补充 |
| 挂号确认卡 | 展示服务对象、医生、日期、时段和地点，二次确认后提交 | 待补充 |

##### 3.2.1.1 智能导诊与挂号详细说明

需求说明：

1. 患者首次进入时展示导诊、用药注意和健康管理三个推荐提问；发送首条消息时才创建会话。
2. Agent 围绕部位、时长、性质和伴随症状进行必要追问，不得为凑轮次提出与当前导诊无关的问题。
3. 每次患者症状输入先由 server-java 执行红线症状规则。命中时立即停止普通导诊，显示红色警告并建议尽快就医或拨打 120，不再调用推荐和挂号工具。
4. 未命中红线时，推荐结果只包含已启用、已配置擅长病症且存在已发布排班的医生。
5. 医生推荐卡必须说明本次推荐理由，并显示医生擅长病症、可预约时段和实时剩余号源。
6. 没有可用号源时，明确告知无号，并提供更换日期、医生或医院的入口，不得展示可提交的虚假时段。
7. 患者提交挂号前二次确认当前健康档案、医生、日期和时段。重复点击或网络重试不得创建重复挂号单。
8. 挂号成功后展示挂号单编号、状态、就诊地点、楼层、携带材料和注意事项；同时提示病情摘要已发送给医生。
9. C 端挂号单与 B 端接诊台读取同一业务记录，医生能够看到本次导诊生成的病情摘要。
10. 所有 AI 回复、病情摘要和推荐解释均显示免责声明标注。

##### 3.2.1.2 会话与交互详细说明

需求说明：

1. 会话列表按最近活跃时间倒序排列，最多展示 50 条，支持新建、恢复和单条删除。
2. 会话归属患者账号，不随健康档案切换；当前轮次需要个性化信息时读取当前激活档案。
3. 删除会话只删除对话数据，不得删除挂号单、处方或报告解读等已形成的业务记录。
4. 对话过程中展示“正在检索知识、正在查询号源、正在锁定号源”等真实工具状态；不得播放与实际调用不一致的固定动画。
5. 语音输入完成识别后，患者可在发送前检查和修改文本。

#### 3.2.2 我的挂号页面

页面功能概述：患者查看本人当前健康档案的挂号单、就诊信息和业务状态。

需求说明：

1. 列表展示挂号单编号、患者姓名、医院、科室、医生、日期、时段和状态，按就诊时间排序。
2. 点击挂号单进入详情，展示就诊地址、楼层、序号、携带材料、病情摘要状态和取消入口。
3. 只有“已约”挂号单可以取消；已接诊或已取消记录不展示取消按钮。
4. 取消成功后状态变为“已取消”，号源只返还一次，B 端医生待接诊列表移除该记录。
5. 接诊完成后 C 端同步显示“已接诊”，并可进入就诊小结和关联处方。

#### 3.2.3 健康档案与时间线页面

页面功能概述：患者创建本人或家人的健康档案，并按服务对象查看健康业务记录。

| 模块 | 需求说明 | 图示 |
|---|---|---|
| 档案切换 | 展示本人及家人档案，当前档案有明确选中状态 | 待补充 |
| 基础资料 | 姓名、性别、出生日期、与账号关系等虚构演示信息 | 待补充 |
| 过敏史 | 支持新增和删除药品或成分类过敏信息 | 待补充 |
| 健康时间线 | 按时间展示挂号、处方、报告解读和就诊小结 | 待补充 |
| 服药打卡 | 展示当日提醒、打卡状态和连续天数 | 待补充 |

需求说明：

1. 未创建档案时，AI 诊室展示建档引导，但普通导诊仍可使用。
2. 涉及挂号、禁忌判断或报告个性化解读时，页面必须显示当前服务对象。
3. 切换档案后只切换健康业务数据，不过滤或迁移账号下的历史会话。
4. 系统无法读取有效过敏史时，不得声称已经完成个性化禁忌检查。

#### 3.2.4 处方详情页面

页面功能概述：患者查看审核通过的电子处方及其通俗解读。

需求说明：

1. 处方详情展示处方编号、医生、开具时间、审核状态、药品名称、规格、用法用量和医嘱。
2. 待审核或已驳回处方不得作为有效处方向患者展示；可通过站内消息说明仍在审核或未通过。
3. 处方解读必须忠实于原处方，不得修改剂量、频次或疗程。
4. AI 解读区分原始处方信息与解释内容，展示注意事项、需要联系医生的情况和免责声明标注。
5. 历史处方使用开具时的药品信息快照，不因药品目录后续修改而变化。

#### 3.2.5 报告与图片解读页面

页面功能概述：患者通过拍照、相册或 PDF 上传健康材料并获得通俗解释。

需求说明：

1. 检查报告支持图片和 PDF；药盒、皮肤、饮食、舌苔场景支持拍照或相册图片。
2. 上传前提示支持格式和大小限制；识别失败、文件损坏或关键区域模糊时要求重新上传。
3. 报告解读区分原始指标、参考范围、通俗说明和建议，不得生成新的诊断结论。
4. 药盒识别结果可结合当前健康档案进行禁忌提示；无法确定具体药品时不得给出确定性用药建议。
5. 皮肤、饮食和舌苔属于 P2 健康建议能力，结果必须注明局限性和免责声明标注。
6. 成功结果保存为独立解读记录，并显示在当前健康档案时间线。

#### 3.2.6 登录、找医院与体验能力

页面功能概述：提供进入产品、查找附近医院和使用辅助交互能力的统一入口。

需求说明：

1. 患者通过 mock 支付宝身份进入 C 端，无需再次注册；登录失败时提示重试，不得进入他人健康档案。
2. “找医院”获得地理位置授权后，按距离展示启用医院、地址和距离；拒绝授权时仍允许按名称或科室查询，不强制开启定位。
3. 患者可直接输入药品名称查询说明和注意事项。查询结果必须区分药品业务资料、知识检索结果和个性化禁忌提示。
4. AI 思考档位提供自动、快速回答和深度思考三种选择，默认自动；切换后从下一轮请求生效，不改变历史消息。
5. 识别到焦虑情绪时可调整界面氛围并使用安抚式表达，但不得弱化红线症状、禁忌或尽快就医提示。
6. 挂号成功后发送站内关怀消息和就诊指引；接诊完成后生成就诊小结，并进入当前健康档案时间线。
7. TTS 播放只朗读当前选中的 AI 回复，支持暂停和重新播放；不得自动播放患者敏感内容。

#### 3.3.3 基础资料管理

需求说明：

1. 医院、科室、医生、排班和药品列表支持按核心字段搜索、筛选和分页。
2. 每名启用医生必须配置至少一个擅长病症或亚专科标签；B 端列表、详情和 C 端推荐卡均应体现。
3. Agent 推荐医生时综合科室、擅长病症、已发布排班和剩余号源；未配置擅长、已停用或无号医生不得进入推荐结果。
4. 已产生排班或挂号记录的医生不得物理删除，只能停用；停用不改变历史记录。
5. 已被处方引用的药品不得物理删除，只能停用；历史处方保留开具时的药品快照。
6. 排班发布后才对 C 端可见；存在已约挂号时执行停诊，系统必须提示管理员处理受影响患者。

#### 3.3.4 医生工作台

需求说明：

1. 医生登录后只展示本人今日排班和本人排班下的挂号单。
2. 接诊列表展示挂号单编号、患者、时段、当前状态和病情摘要生成状态。
3. 医生打开接诊详情后，可查看带免责声明的病情摘要和当前健康档案中的过敏安全信息。
4. 医生填写诊断结论与医嘱后将挂号单标记为“已接诊”；已接诊和已取消挂号不得重复接诊。
5. 每个电子处方必须关联一条已接诊记录。医生只能从启用药品目录选药，并填写用法、单次剂量、频次和疗程。
6. 提交处方前必须执行过敏和相互作用规则。明确禁忌阻止提交；谨慎使用提示风险依据并要求医生确认。
7. 提交后处方进入“待审核”，医生不能直接改为“已通过”；驳回后可按原因修改并重新提交。

#### 3.3.5 处方审核

需求说明：

1. 审核列表默认展示待审核处方，支持按医生、患者、日期和状态筛选。
2. 审核详情展示诊断结论、药品、规格、用法用量、规则检查结果和医生确认记录。
3. 管理员选择通过时记录审核人和时间；患者随后收到站内消息并可查看处方。
4. 管理员驳回时必须填写原因；医生可见原因并可修改后重新提交。
5. 待审核和已驳回处方不得在患者侧展示为可执行处方。
6. 已通过版本不可编辑；任何修改必须产生新的可追踪审核轮次。

#### 3.3.6 运营与审计

需求说明：

1. 数据看板统计今日挂号量、科室分布、号源使用率、Agent 会话量和工具调用次数，并标明统计时间范围。
2. Agent 日志只记录脱敏摘要、工具名、参数类型、执行结果和耗时，不记录患者敏感原文。
3. 医学知识图谱展示五类节点及关系，支持节点筛选和查看详情，默认不提供业务实体写入能力。
4. 演示数据重置必须二次确认，仅重置固定虚构数据；不得展示或打印环境变量及连接凭据。

### 3.4 非功能需求

| 类型 | 需求说明 |
|---|---|
| 医疗安全 | 红线症状与用药禁忌由 server-java 确定性规则处理；所有 AI 产出显示“仅供参考，不替代医生诊断” |
| 数据一致性 | 号源使用 Redis 原子 DECR 与 PostgreSQL 事务对账，禁止先查后改；取消只返还一次 |
| 权限安全 | server-java 是唯一对外入口并统一鉴权和审计；医生只能处理本人排班数据，管理员不能代写诊断 |
| 隐私安全 | .env 不入库、不打印；日志与 Agent trace 不记录患者敏感原文，只保存脱敏摘要和参数类型 |
| 性能体验 | 对话通过 SSE 流式展示；耗时工具调用必须展示真实进度状态；普通列表支持分页 |
| 兼容性 | C 端在支付宝小程序开发者工具模拟器完成主验收；B 端支持项目指定的 Chromium 内核浏览器 |
| 可用性 | 无号、识别失败、LLM 调用失败和业务回调失败均给出可理解的下一步，不展示伪成功结果 |
| 可测试性 | server-java 使用 MockMvc 测外部行为；server-py 使用 TestClient 和 fake 依赖断言工具顺序 |
| 数据管理 | PostgreSQL 存业务实体，Neo4j 只存医学知识，Redis 只由 server-java 操作号源计数；禁止双写 |
| 可演示性 | 主闭环不依赖人工改库或两套静态数据；两端均从登录开始实测且无控制台错误 |

### B. B+C 主闭环验收

使用同一套虚构演示数据按顺序执行。步骤之间禁止人工改库、重置数据或替换前端静态结果；每一步生成的业务编号和状态必须作为下一步输入。

| 编号 | 前置条件 | 用户操作 | 可观察结果 | 闭环证据 |
|---|---|---|---|---|
| AC-01 | 管理员已登录 B 端 | 配置医生科室、擅长病症并启用，创建并发布排班 | 医生资料和真实号源可用 | C 端推荐内容与 B 端资料、时段和余号一致 |
| AC-02 | 管理员已登录 B 端 | 新增药品业务资料并启用 | 药品出现在启用目录 | 医生开方页可检索，停用后不可加入新处方 |
| AC-03 | 普通演示患者进入 C 端 | 输入非红线症状并回答追问 | 展示科室和医生推荐卡 | 推荐医生来自 AC-01，包含理由、擅长病症和号源 |
| AC-04 | 推荐时段仍有号 | 患者确认医生、时段和健康档案 | 创建唯一“已约”挂号单，号源减 1 | 医生接诊台出现相同编号、患者、时段和病情摘要 |
| AC-05 | 医生使用 doctor.lin / doctor123456 登录 | 查看摘要，填写诊断与医嘱并接诊 | 挂号单变为“已接诊” | C 端同一挂号单同步状态且不可取消 |
| AC-06 | 接诊已完成，药品启用且未命中禁忌 | 医生开方并提交 | 处方进入“待审核” | 管理员看到同一处方编号，患者尚不可作为有效处方查看 |
| AC-07 | 管理员使用 admin / admin123456 登录 | 审核通过处方 | 处方变为“已通过” | 医生看到结果，患者收到消息并在时间线看到同一处方 |
| AC-08 | 处方已通过 | 患者打开处方详情 | 展示原处方和通俗解读 | 药品及用法一致，AI 解读带免责声明标注 |

AC-01 至 AC-08 连续通过，才认定主闭环成立。仅展示页面、接口返回成功或分别使用互不关联的 mock 数据不算通过。

### C. 关键异常验收

| 编号 | 场景 | 验收结果 |
|---|---|---|
| AC-E01 | 输入胸痛伴冷汗等红线样例 | 先于推荐触发红色警告，不调用推荐或挂号工具，不创建挂号单；普通输入不误触 |
| AC-E02 | 推荐科室所有排班无号 | 不展示可提交的虚假时段，提供更换日期、医生或医院入口 |
| AC-E03 | 同一挂号连续点击或幂等重试 | 只产生一个挂号单，只扣减一个号源 |
| AC-E04 | N 个并发请求抢最后 1 个号源 | 恰好 1 个成功，Redis 与 PostgreSQL 一致，失败请求无挂号单 |
| AC-E05 | 取消一个已约挂号并重复取消 | 首次取消返还 1 个号源，B 端移除待接诊记录；重复取消不再返还 |
| AC-E06 | 健康档案过敏信息命中明确禁忌 | server-java 阻止提交，不产生待审核处方，医生看到命中药品和规则类型 |
| AC-E07 | 管理员驳回处方 | 患者侧不展示为有效处方，医生可见原因并可修改重提，审核轨迹保留 |
| AC-E08 | 检查全部 AI 产出 | 导诊建议、病情摘要、处方/报告解读、图片分析和就诊小结均显示免责声明标注 |

### D. 范围与 Mock 边界

范围外：

- 实时医患 IM、视频问诊、真实支付、随访计划真实执行、商保快赔。
- 家庭账户的跨账号成员和授权体系；同一账号下创建本人或家人档案属于范围内。
- 微服务拆分、异地多活、端到端 RTC 语音、订阅消息真推送、小程序上架与审核。

Mock 能力：

- 支付宝登录、药店推荐、购药下单和支付使用 Mock。
- Mock 链路必须有完整可演示反馈，例如“点击下单 → 成功态”；不得用 Mock 替代挂号、接诊和处方审核主闭环。

### E. 实施边界

- C 端采用支付宝原生小程序和 antd-mini；禁止使用微信小程序文件格式和 wx API。
- B 端采用 React、TypeScript、Umi、Ant Design、AntV 和 Zustand。
- server-java 是唯一对外入口和业务写入方，负责鉴权、审计、规则引擎、号源与全部业务 API。
- server-py 只负责 Agent 编排、LLM/语音调用和知识检索；业务写入必须经 HTTP 工具回调 server-java。
- PostgreSQL 存业务实体，Neo4j 只存医学知识图谱，Redis 号源计数仅由 server-java 操作。
- 所有本地应用和测试在本地运行并直连已部署的数据服务；日常开发不得执行 Docker Compose 启动或远程维护。
- Schema 使用 schema.sql 与幂等 seed 管理，不使用迁移工具。
- 演示数据必须使用虚构信息。固定账号为 admin / admin123456、doctor.lin / doctor123456。
- 提供并发抢最后一个号源的脚本，现场证明成功数不超过剩余号源且 Redis 与 PostgreSQL 一致。
