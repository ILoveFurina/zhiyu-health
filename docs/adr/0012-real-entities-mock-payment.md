# 药品订单与挂号收费：实体真实、支付 Mock

Status: accepted（refines ADR-0008）

ADR-0008 将"登录、购药、支付"整体钉在 mock 边界内。随着药品售卖模块与挂号收费纳入 demo 范围，购药与收费需要真实的后端业务实体（订单、收费记录、库存、状态流转）和 B 端管理面，但接入真实支付网关（支付宝/微信支付沙箱、回调幂等、对账）在两周 demo 周期内风险失控，且当年正是为此引入该边界。

决策：把 ADR-0008 的"购药/支付 mock 边界"细化为**"业务实体真实、支付动作 Mock"**：

- 药品订单（`drug_orders` + `drug_order_items`）、挂号收费字段（appointments 增 `registration_fee`、新增 `payments` 收费记录表）为**真实业务实体**，进 PostgreSQL，由 server-java 唯一写入，纳入审计与 B 端管理面。
- 支付动作维持 Mock 状态机：用户点击"模拟支付"将订单/收费记录从 `UNPAID` 一键置为 `PAID`，**不接入任何支付网关、不接收真实回调**。状态流转契约入 `contracts/`，双栈只读消费。
- 药品库存为真实业务字段（medications 增 `price/stock` 或新建库存表），下单扣库存走 server-java 事务，与号源扣减同理不得先查后改。
- 药品业务数据（价格/库存）只存 PostgreSQL，不进 Neo4j（ADR-0006 边界不变）。

被否决的方案：

- 纯前端 Mock（维持现状）：无后端实体、无 B 端管理面，"模块"名不副实，评审无可演示数据。
- 接真实支付沙箱：支付网关集成、回调幂等、对账在两周 demo 内风险失控，与 ADR-0008 当初挡住的风险同源。

后果：B 端需新增"药品管理""订单管理""收费管理"页面；C 端购药入口由纯前端 Mock 升级为调 server-java 下单接口；demo 演示时需向评审说明"支付为模拟动作，未接真实网关"。
