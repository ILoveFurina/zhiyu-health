# 中医辨证场景合规边界：调理不出药材 + 中医专属免责 + 急症软兜底

Status: accepted（票 17 拍舌苔/中医辨证）

票 17 拍舌苔是首个引入中医语义的票，相比 15 拍皮肤 / 16 拍饮食有更严的合规负担：中医"体质辨证"本身是中医诊断行为，"调理建议"常含药材/方剂，与硬约束 2"C 端 Agent 不做个性化用药决策"存在灰色地带。本 ADR 收口三条合规边界，使中医场景在符合既有用药决策硬约束的前提下可演示。

## 决策

1. **调理建议只讲方向，不出现具体药材/方剂/剂量。** 体质辨识后给出的是"调理方向"（作息/运动/饮食原则/通用食材如山药红枣等日常食物），不出现纯药材（如黄芩/附子）、方剂名或任何剂量。这使 17 严格落在硬约束 2 与 ADR-0016"通用知识解释"白名单内，不触碰"个性化用药决策"红线。prompt 必须显式约束 LLM 不得输出药材名与剂量。

2. **`contracts/disclaimer.json` 新增中医专属免责文案。** 现有通用文案"仅供参考，不替代医生诊断"覆盖不到"面诊"这一中医特定语义。舌诊卡片叠加通用免责 + 中医免责（"体质辨识仅供参考，不替代中医面诊"）两条。保留单一 disclaimer.json 契约文件，中医文案与通用文案并列，双栈同步加载。

3. **舌象急症只做软兜底，不扩红线引擎。** 舌象识别出可能指向重病的特征（如镜面舌/霉酱苔）时，由 prompt 引导 LLM 输出"建议尽快就医"软话术，不将视觉结果回流到 `RedFlagRuleEngine` 确定性规则通道。红线引擎维持只接受文本 `judge(String text)` 的现状，不为视觉场景扩展。与 15 拍皮肤"异常描述时建议就医"软兜底先例同构。

## 为什么不为中医场景开"药材"口子

- ADR-0016 已明确"C 端 Agent 不做个性化用药决策"，体质辨证 + 药材推荐 = 典型的个性化用药决策，开此口子需要新 ADR 推翻 ADR-0016 的适用范围，成本高且违背选题硬约束。
- 两周 demo 范围内，"调理方向"已足够演示中医体质辨证的差异化体验，药材推荐不是评审必需项。
- 药材推荐涉及药食同源边界判定（哪些算食材、哪些算药材），需要白名单契约与校验逻辑，超出 17 的合理工作量。

## 为什么不扩红线引擎扫舌象

- `RedFlagRuleEngine` 是 server-java 确定性规则，设计为对**用户文本**做关键词匹配。视觉分析结果（结构化体质辨识）是 LLM 产出，性质不同于用户主动输入的文本，强行塞进红线引擎会模糊"确定性规则只处理用户输入"的边界。
- 舌象与急症的关联在中医里本身是概率性判断（镜面舌未必是急症），不适合做"命中即中断 + 120"的确定性红线处理。软兜底"建议就医"更符合中医辨证的不确定性本质。
- 扩红线引擎接受视觉结果需改 `RedFlagRuleEngine` 签名 + 视觉链路回流，工作量与两周 demo 收益不成比例。

## Consequences

- 17 的 prompt 必须显式约束：体质辨识产出 + 调理方向（作息/运动/饮食原则/通用食材），禁止药材/方剂/剂量。prompt 设计与 15/16 不同，需单独编写并加强约束。
- `contracts/disclaimer.json` 从单文案变为多文案（通用 + 中医），加载方需按场景取用：舌诊卡片取通用 + 中医两条，其他 AI 产出仍只取通用。
- 舌象急症不走红线中断，仅软兜底；若评审质疑"为何舌象急症不弹红色警告"，依据本 ADR 第 3 条解释。
- 未来若有其他中医场景（如脉象辨识），应沿用本 ADR 三条边界，不重复决策。
