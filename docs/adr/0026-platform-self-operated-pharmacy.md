# 药品履约：平台自营药房，不做处方外流与多药店

Status: accepted

题目 C 端"药店推荐（价格/距离/配送时效）"与 B 端"药品库存同步（与药店数据打通）"暗示处方外流生态（外部零售药店网络履约，平台聚合其库存），但题目同时允许"可用 Mock 数据简化处方、购药等环节"。medications 为全局药品目录与库存（无 hospital_id、无药店外键），需要明确其领域语义，避免"医院药房"与"处方外流"两种误读。

决策：药品履约采用**平台自营药房**模型——平台运营方自有的中心药房统一持有全部药品库存（medications 全局一份），APPROVED 处方发起的药品订单由其统一履约，不区分医院、不引入任何药店实体。B 端药品/库存/订单管理即平台运营方对自营药房的管理，与"药师职责并入 admin"（spec 条目 26）一致。

被否决的方案：

- 医院药房模型：库存需按医院拆分，seed 两家医院共享一份库存在语义上讲不通，且履约绑定就诊医院对 demo 闭环无增量价值。
- 处方外流 / 多药店模型（题目建议的完整形态）：需 pharmacies 实体、按药店拆库存、订单带 pharmacy_id、库存同步通道乃至药店端身份。属真实产品外延，评分维度（Agent 智能度/闭环完整性/创新性/体验/架构）中无对应加分点，demo 周期内不实现。

后果：C 端无"药店推荐"环节，处方 APPROVED 后直接由平台药房下单履约；答辩口径为"购药采用平台自营药房，多药店比价与配送对接属处方外流生态，按题目允许范围 Mock 简化"。票 09 早期 checklist 的"静态药店推荐 + Mock 下单"入口已被真实药品订单（ADR-0012）取代，不再回退。
