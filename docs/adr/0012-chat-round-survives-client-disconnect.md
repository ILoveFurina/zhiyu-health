# 已接受的对话轮次不随客户端断连取消

Status: accepted

C 端实时连接只是对话轮次的观察通道，不拥有轮次生命周期。server-java 一旦完成鉴权、确定性规则检查并接受一轮对话，即使小程序断网、离开页面或 WebSocket 关闭，也继续驱动 server-py 完成生成与工具编排并持久化最终结果；用户重新进入后从对话记录恢复完整回答。这一语义对标同类头部健康 AI 产品的匿名黑盒实测行为，并避免为了恢复界面而重放可能触发挂号等业务副作用的请求。

对话轮次是 PostgreSQL 中的一等业务实体，以 `(patient_id, request_id)` 唯一标识并记录 `ACCEPTED / RUNNING / COMPLETED / FAILED` 生命周期；消息与最终结果仍按既有模型持久化。Redis 不参与轮次状态：当前 server-java 为单实例，状态访问低频，缓存不能改善模型 TTFT，也不能让进程崩溃后的 Agent 继续执行；运行任务和实时观察者仅保存在进程内，丢失后由 PostgreSQL 中的遗留运行态收敛为失败而不自动重放。

## Consequences

- 断连只移除实时订阅者，不取消已经接受的上游 Agent 调用；300 秒总超时仍是失控任务的资源回收上限。
- 客户端不自动重发未完成轮次；重新连接后先同步当前会话记录。
- 用户离开后仍可能产生模型费用和业务工具调用，这是换取完整历史与无重复副作用恢复语义的明确代价。
- WebSocket 是小程序实时入口，HTTP SSE 仅保留为诊断和非小程序适配器；两者共用同一个持久化轮次服务和 `request_id` 幂等边界，不拥有各自的业务流程。
- 断线后不做自动重新附着：客户端恢复路径为重进页面拉取对话记录。WebSocket 建连失败时可用同一 `request_id` 回退 SSE，这只恢复观察通道，不重新运行 Agent。只有用户明确重试才创建新的 `request_id` 和对话轮次。
