> 本文为扩展产品说明；施工与验收的唯一权威 Spec 位于 `.scratch/zhiyu-mvp/spec.md`，两者冲突时以后者为准。

版本：v1.0  
日期：2026-07-28  
项目周期：两周（约 14 日历天）  
团队规模：3–5 人，三线并行（小程序 / B 端 / 后端+AI）

## 1 项目概述

### 1.1 产品定位

智愈是一个 AI 驱动的全链路医疗健康平台，由 C 端支付宝原生小程序（医疗 AI Agent）和 B 端 React 管理后台组成。C 端 AI Agent 不是问答机器人，而是能调用 API 完成真实业务闭环（挂号、处方解读、报告分析）的智能助手；B 端为 Agent 提供数据支撑并赋能医生。

### 1.2 问题陈述

患者就医前不知道挂什么科、挂哪个医生，流程繁琐且无人引导；医生接诊前对患者一无所知，诊疗效率低。智愈旨在通过 AI Agent 打通"症状描述 → 智能导诊 → 医生推荐 → 挂号 → 接诊 → 处方 → 解读"全链路，实现 B+C 深度联动。

### 1.3 核心价值主张

- 患者侧：零门槛、自然语言交互完成导诊挂号全流程，附带情感化关怀与多模态健康服务
- 医生侧：接诊前即获得 AI 整理的病情摘要，提升诊疗效率
- 运营侧：数据看板实时掌握运营全貌，知识图谱可视化管理医学知识资产
- 技术侧：确定性规则引擎保障医疗安全，LLM 仅负责表达与解释

## 3 系统架构概述

### 3.1 技术栈

| 层次 | 技术选型 | 说明 |
|------|----------|------|
| C 端 | 支付宝原生小程序 + antd-mini | AXML + my.* API，语音用火山引擎 |
| B 端 | React + TypeScript + Umi + Ant Design + AntV + Zustand | 赛题硬约束，禁用 Vue |
| 业务后端（server-java） | Java / Spring Boot / MyBatis-Plus | 唯一对外入口与唯一业务写入方 |
| Agent 层（server-py） | Python 3.12+ / FastAPI / LangChain + LangGraph / uv | 对话编排、LLM/语音对接、知识检索 |
| LLM | 火山方舟 doubao-seed-2.1-turbo（对话/视觉）+ doubao-embedding-vision（向量化） | OpenAI 兼容协议 |
| 存储 | PostgreSQL 16 + pgvector / Redis 7 / Neo4j 5 | 业务+向量 / 号源计数+缓存 / 医学知识图谱 |

### 3.2 请求链路

端 → server-java（鉴权/审计/限流 → 规则引擎 → 业务写入）→ 对话类请求经 SSE 流式调 server-py → LLM/工具 → token 逐跳透传回端。

### 3.3 数据访问权边界

| 数据 | 写入方 | 读取方 |
|------|--------|--------|
| 业务表（PostgreSQL） | 仅 server-java | server-java + server-py（只读向量检索） |
| Redis 号源计数 | 仅 server-java | server-java |
| Neo4j 医学知识图谱 | 初始化 seed | 仅 server-py 直连 |

### 3.4 运行拓扑

开发数据库部署于云服务器（Docker Compose 仅供人工部署维护），团队通过安全组白名单直连；server-java、server-py、B 端、小程序开发环境与全部测试均在本地运行。未经用户明确授权，Agent 禁止 SSH 登录或修改云端服务；小程序以开发者工具模拟器为主演示，真机通过预览二维码 + 真机调试代理访问本地 server-java。

## 5 非功能需求

### 5.1 安全

- 安全判断走规则不走 LLM：红线症状、用药禁忌由 server-java 的确定性规则引擎判断，LLM 只做表达与解释
- 密钥管理：.env 永不入库、不打印、不写进代码或测试
- 审计日志与 Agent trace 不落患者敏感原文，只记录脱敏摘要、工具名、参数类型与执行结果
- 审计统一在 server-java 入口落

### 5.2 数据一致性

- 号源防超卖：Redis 原子 DECR + PG 事务对账，禁止先查后改
- schema 管理：schema.sql + 幂等 seed（server-java 启动时执行），开发期 drop + recreate + seed

### 5.3 可演示性

- 演示主线 5 分钟：症状 → 情感化追问 → 推荐 → 挂号 → 切 B 端接诊台看摘要 → 开方 → 回 C 端处方解读
- 支线亮点：图谱可视化、过敏禁忌拦截、并发防超卖
- Seed 规模：2 医院、6–8 科室、15–20 医生、未来 7 天排班、15–20 症状场景图谱数据、30–50 药品 + 禁忌规则、演示账号（患者 2 / 医生 2 / 管理员 1）

### 5.4 可插拔性

- 每个功能模块可插拔，演示主线只依赖 P0+P1
- 支线亮点（含图谱可视化）按完成情况插拔

## 7 核心业务流程

### 7.1 智能导诊挂号主流程

```
患者描述症状（文字/语音）
  → Agent 多轮追问（部位/时长/性质）
  → [规则引擎] 红线症状检测
    → 命中：中断导诊，红色警告，建议就医/拨打 120
    → 未命中：继续
  → Agent 检索知识（pgvector + Neo4j）推荐科室
  → 查询该科室医生排班与号源
  → 推送结构化医生推荐卡片
  → 患者选定医生与时段
  → Redis 原子 DECR 扣减号源 + PG 事务写挂号单
  → 生成病情摘要发送接诊医生
  → 推送就诊指引卡 + 主动关怀消息
```

### 7.2 接诊与处方流程

```
医生登录工作台 → 查看接诊台
  → 查看患者 AI 病情摘要
  → 标记已接诊
  → 开具电子处方（药品表选药 + 用法用量）
    → [规则引擎] 过敏/禁忌自动警告
  → 提交处方 → 管理员（药师）审核（通过/驳回）
  → 审核通过 → C 端患者收到处方通俗解读
  → 接诊完成 → Agent 生成就诊小结推送患者
```

### 7.3 报告解读流程

```
患者上传报告图片/PDF
  → 视觉模型（doubao-seed-2.1-turbo）识别内容
  → RAG 检索相关医学知识
  → 生成通俗解读（附免责声明）
  → 存入 report_interpretations
  → 时间线可查
```

- 录屏兜底方案就绪

### 14.2 技术验收

- 防超卖：N 并发抢最后 1 个号源，恰好 1 个成功，Redis 与 PG 计数一致
- 红线症状：危险输入必触发、正常输入不误触（规则引擎单测覆盖）
- Agent 行为：fake LLM 断言工具调用序列与业务回调正确
- 禁忌规则：过敏史 × 药品 → 拦截/放行（service 层单测）

### 14.3 测试策略

- server-java 主 seam：HTTP API 层（MockMvc），只测外部行为
- server-py 主 seam：Agent HTTP 接口层（TestClient），LLM 用 fake 替换
- 前端两端不写自动化测试，以演示剧本手动验收
