# 智愈 MVP 规格（Spec 0001）

Status: ready-for-agent
日期： 2026-07-27 · 周期： 两周（约 14 日历天）· 团队假设： 3–5 人，三线并行（小程序 / B 端 / 后端+AI）

## Problem Statement

患者就医前不知道挂什么科、挂哪个医生，流程繁琐且无人引导；医生接诊前对患者一无所知，诊疗效率低。题目要求构建 B+C 深度联动的医疗平台：C 端 AI Agent 不是问答机器人，而是能调用 API 完成真实业务闭环（挂号、下单、预约）的智能助手；B 端为 Agent 提供数据支撑并赋能医生。评审交付场景：可现场演示的完整业务闭环 + AI 创新亮点。

## Solution

微信原生小程序（C 端）：医疗 AI Agent 完成"症状描述 → 追问 → 科室 → 医生推荐 → 挂号"全闭环，全程情感化交互（情绪识别、主动关怀、语音多模态），并附处方解读、报告解读、健康档案。Vue3 Web 管理后台（B 端）：医院/科室/医生/排班/号源管理，医生工作台（接诊台看病情摘要、开电子处方），医学知识图谱可视化，数据看板。后端为全 Python（FastAPI）单体（ADR-0001），存储 PostgreSQL+pgvector / Redis / Neo4j（ADR-0003、0006），LLM 用火山方舟 doubao（ADR-0004），Agent 编排 LangChain + LangGraph（ADR-0005）。

## User Stories

**C 端（患者）**

1. 作为患者，我想微信内打开小程序免注册使用（登录 mock），以便零门槛开始。
2. 作为患者，我想用文字或语音描述症状，以便最自然地表达。
3. 作为患者，我想 Agent 围绕症状追问细节（部位/时长/性质），以便导诊更准确。
4. 作为患者，我想在对话中实时看到 Agent 的工作状态（正在检索知识/查询科室号源/锁定号源），以便确信它在真实办理业务而非闲聊。
5. 作为患者，我想收到结构化医生推荐卡片（照片/职称/擅长/剩余号源），以便快速选择。
6. 作为患者，我想选定医生与时段并完成挂号，号源实时扣减，以便锁定号源。
7. 作为患者，我想挂号成功后得知病情摘要已发送给接诊医生，以便就诊时被了解。
8. 作为患者，我想查看与取消我的挂号单（取消返还号源），以便行程变更。
9. 作为患者，我想收到电子处方的通俗语言解读，以便理解用药方法。
10. 作为患者，我想上传检查报告图片获得通俗解读，以便看懂指标。
11. 作为患者，我想所有 AI 产出都带"仅供参考，不替代医生诊断"免责声明标注，以便明确边界。
12. 作为患者，我想焦虑时得到安抚式回应（情绪识别体现在 UI 与文案），以便感到被关怀。
13. 作为患者，我想挂号成功后收到主动关怀（就诊注意事项提醒，站内消息），以便做好准备。
14. 作为患者，我想听到 AI 回复的语音播报，以便不便阅读时使用。
15. 作为患者，我想以时间线查看我的挂号/处方/报告记录，以便追踪健康历史。
16. 作为登记了过敏史的患者，我想 Agent 推荐药品时自动避开我的过敏药物（禁忌拦截），以便安全。

**B 端（管理员）**

17. 作为管理员，我想账号密码登录后台（与患者账号体系分离），以便安全管理。
18. 作为管理员，我想管理医院（等级/地址 CRUD），以便维护机构数据。
19. 作为管理员，我想管理科室（隶属医院），以便维护科室设置。
20. 作为管理员，我想管理医生（隶属科室/职称/擅长），以便维护出诊资源。
21. 作为管理员，我想为医生设置排班（日期/时段/号源总数），以便放号。
22. 作为管理员，我想在数据看板看到今日挂号量、科室分布、号源使用率、Agent 对话量与工具调用次数，以便掌握运营全貌。
23. 作为管理员，我想查看医学知识图谱可视化（ECharts 力导向图，节点点击看详情），以便展示医学知识资产。
24. 作为管理员，我想查看 Agent 调用日志（每轮对话的 tool trace），以便审计与演示。
25. 作为管理员，我想一键重置演示数据（re-seed），以便反复排练演示。
26. 作为管理员（药师角色并入），我想审核电子处方（通过/驳回），以便把关用药安全。

**B 端（医生）**

27. 作为医生，我想登录工作台看到今日排班与接诊台，以便开始接诊。
28. 作为医生，我想在接诊台查看挂号患者的 AI 病情摘要，以便快速了解病情。
29. 作为医生，我想开具电子处方（药品表选药 + 用法用量），以便完成诊疗。
30. 作为医生，我想将挂号单标记为已接诊，以便状态流转。

**C 端补充（第二轮拷问追加，已确认）**

31. 作为患者，我想上传体检报告（拍照、相册图片或 PDF 文件）获得通俗解读，以便看懂指标。
32. 作为未创建健康档案的患者，我想在 AI 页看到引导卡片，一键创建档案（基础信息 + 过敏史），以便获得个性化与用药安全服务。
33. 作为患者，我想在 AI 页初始看到三个推荐提问（导诊/用药注意/健康管理各一），以便快速开始对话。
34. 作为患者，我想说出症状或科室后，基于当前地理位置获得就近医院推荐（含距离），以便选择方便的就诊地点。
35. 作为患者，我想自选 AI 思考档位（自动 / 快速回答 / 深度思考），以便在速度与推理深度间权衡。
36. 作为患者，我想拍药盒照片获取药品说明书与用药注意事项（含过敏禁忌提醒），以便安全用药。
37. 作为患者，我想在聊天框上方看到功能入口气泡（AI 诊室/找医院/看报告/拍药盒/拍皮肤/拍饮食/拍舌苔），点击后出现内嵌操作组件的引导卡片，以便发现并直接使用各项功能。
38. 作为患者，我想拍摄面部/皮肤照片获得肤质分析与护理建议，以便了解皮肤状况。
39. 作为患者，我想拍摄饮食照片获得营养与热量评估及建议，以便管理饮食健康。
40. 作为患者，我想拍舌苔照片获得中医体质辨证与调理建议，以便了解中医视角的健康状况。
41. 作为患者，我想症状危险（如胸痛伴冷汗）时被 Agent 立即中断导诊、红色警告并建议尽快就医或拨打 120，以便关键时刻不被耽误。
42. 作为患者，我想为家人（如父母）创建并切换健康档案，以便帮家人解读报告与管理健康。

**B 端（医生）补充**

43. 作为医生，我想开处方时被自动警告当前健康档案的过敏信息与药品相互作用，以便保障用药安全。

**C 端补充（续）**

44. 作为患者，我想按提醒服药打卡并查看连续打卡天数，以便坚持用药。
45. 作为患者，我想直接输入药名查询说明书与注意事项，以便快速查药。
46. 作为患者，我想挂号成功后收到就诊指引卡（地址/楼层/注意事项/携带材料），以便顺利就诊。
47. 作为患者，我想接诊完成后收到 Agent 生成的就诊小结，以便回顾诊疗结论。

**系统与演示**

48. 作为系统，挂号扣减必须防超卖：N 个并发请求抢剩余号源时成功者不超过剩余数。
49. 作为演示者，我想有并发抢号脚本现场证明防超卖（D 方向实证）。
50. 作为演示者，我想切换 RAG/图谱增强开关，现场对比裸 LLM 与知识增强的回答差异。
51. 作为演示者，我想云服务器承载开发数据库、本地运行后端与前端，并以开发者工具模拟器为主演示、预览二维码 + 真机调试代理为真机备选，同时准备完整录屏兜底，以防现场 LLM API 抖动。

## Implementation Decisions

- **三端一后端**：微信小程序 C 端（原生 + Vant Weapp，ADR-0002）、Vue3+Element Plus B 端、FastAPI 单体后端（ADR-0001），均全部 AI 生成代码。
- **演示运行拓扑**：开发数据库部署于云服务器 `43.139.160.223`，团队通过账号密码直连，云安全组仅放行团队固定公网 IP；FastAPI、B 端与小程序开发环境在本地运行；小程序以开发者工具模拟器为主，真机通过预览二维码 + 开发者工具真机调试代理访问本地后端，不要求 HTTPS 域名。
- **存储分工**：PostgreSQL 16 存全部业务实体 + pgvector 存知识块向量（ADR-0003）；Redis 承担号源计数与缓存；Neo4j 只存医学知识图谱（症状/疾病/科室/药品/禁忌五类节点 + 边），不装业务实体、无任何双写（ADR-0006）。
- **LLM**：火山方舟一个 key；对话/视觉解读用 `doubao-seed-2.1-turbo`，RAG 向量化用 `doubao-embedding-vision`；C 端对话三档可选（自动/快速回答/深度思考），默认自动——后端按场景分配（导诊走低档、报告解读走高档）（ADR-0004）。
- **Agent**：LangChain + LangGraph 编排（ADR-0005），依赖版本锁死；tool 函数为薄壳（仅参数校验），业务逻辑全在 service 层。第一版工具：`search_knowledge`（pgvector 召回）、`traverse_graph`（Neo4j 一跳扩展）、`recommend_doctors`、`get_doctor_slots`、`create_appointment`、`get_appointment`、`check_contraindication`。
- **领域实体**：patients（C 端 mock 登录身份）、health_profiles（同一患者账号 1:N，基础信息 + 过敏史）、staff_users（医生/管理员，独立账号体系）、hospitals、departments、doctors、schedules（total_slots/remaining_slots，号源池计数 ADR-0007）、appointments（分配序号 + 状态：已约/已取消/已接诊）、condition_summaries、consultation_records（医生填写的诊断结论 + 医嘱）、prescriptions + prescription_items（审核状态流转）、medications（药品业务信息唯一权威来源）、report_interpretations、knowledge_chunks、agent_call_logs、in_app_messages（站内消息通道，票 09 首建）、med_checkin_records（服药打卡/提醒记录）；禁忌与药品相互作用关系唯一来源为 Neo4j 图谱（见 ADR-0006）。
- **API 契约概略**：`/api/c/*`（会话、导诊对话 SSE、推荐卡片、挂号、挂号单管理、处方解读、报告解读、档案时间线）；`/api/b/*`（登录、机构/科室/医生/排班 CRUD、接诊台、电子处方与审核、图谱数据、看板统计、Agent 日志、演示重置）。
- **关键交互**：结构化消息卡片（小程序聊天区自定义消息类型）；工具调用可视化（LangGraph 事件流 → SSE → 小程序进度条 + B 端日志页）；语音输入用微信同声传译插件，TTS 播报同源；情绪标签经 LLM 结构化输出的 emotion 字段驱动 UI 变色与安抚文案；情感化人设集中在 system prompt。
- **硬约束**：免责声明标注为全局 UI 组件 + 后端统一注入，覆盖导诊建议、病情摘要、处方解读、报告解读、拍照分析、就诊小结、LLM 生成的用药解释与替代建议等一切 AI 产出，无例外。
- **Mock 边界**：微信登录、药店推荐、购药下单、支付；Mock 购药仍需具备“点击下单 → 成功态”的可演示反馈。
- **施工纪律**：顺序 P0（导诊挂号主闭环 + B 端基础管理）→ P1（电子处方 + RAG + 禁忌 + 报告解读）→ P2（图谱可视化 + 情感化）→ 档外功能；每个功能可插拔；演示主线只依赖 P0+P1；支线亮点（含图谱可视化）按完成情况插拔。

## Testing Decisions

- **主 seam：FastAPI HTTP API 层**（TestClient），只测外部行为，不测实现细节——这是全局唯一的高层接缝。
- **LLM seam**：LLM 客户端接口可替换为 fake；Agent 行为测试用 fake LLM 断言工具调用序列与业务副作用（如挂号单落库）。
- **防超卖**：API 层并发测试——N 并发抢最后 1 个号源，恰好 1 个成功，Redis 与 PG 计数一致。
- **禁忌规则**：service 层单元测试（过敏史 × 药品 → 拦截/放行）。
- **前端（两端）**：不写自动化测试，以演示剧本手动验收——两周周期的现实取舍。
- 测试依赖由 docker-compose 提供独立的 PG 数据库、Redis DB 与 Neo4j 测试实例，使用 `TEST_DATABASE_URL` / `TEST_REDIS_URL` / `TEST_NEO4J_URI`，不得复用演示数据；本地测试通过安全组白名单内的公网连接访问云端依赖。

## Out of Scope

- 实时医患 IM/视频问诊、支付、随访计划真实执行、商保快赔、家庭账户（跨账号成员与授权体系）、慢病管理计划；同一患者账号下为本人/家人创建并切换多份健康档案属于范围内能力，不等同于家庭账户。
- 微服务拆分、异地多活、隐私计算（仅设计文档叙述，属 D 方向）。
- 端到端实时语音对话（RTC）、订阅消息真推送。
- 小程序上架与审核。
