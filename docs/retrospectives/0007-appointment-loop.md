# Issue 07：挂号闭环的双栈边界与失败语义

- 日期：2026-07-28
- 状态：已验证
- 相关票单：[07-appointment-loop](../../.scratch/zhiyu-mvp/issues/07-appointment-loop.md)
- 相关规则：[AGENTS.md](../../AGENTS.md)、[ADR-0007](../adr/0007-slot-pool-counting.md)、[ADR-0009](../adr/0009-competition-stack-pivot.md)
- 标签：`双栈边界` `幂等` `服务鉴权` `失败语义` `验证`

## 一句话结论

跨 Java/Python 的业务写流程，应先按数据所有权确定编排位置，再设计不可逆提交点、失败降级和重复请求的等价结果。

## 目标与最终结果

目标是完成“导诊推荐医生 → 选择号源 → 创建挂号 → 保存病情摘要 → 查看或取消挂号”的闭环，并保证号源不超卖。

最终由 server-py 的薄壳工具单次回调 server-java；server-java 独占挂号写入和两阶段业务编排。挂号先独立提交，摘要失败仅降级提示；重复请求不重复扣号，也不会覆盖或误报已有摘要。双向回调均要求显式服务凭据。

## 碰壁记录

### 1. 把确定性流程交给模型

- 当时的判断：创建挂号后，让模型再次调用摘要工具，接口拆分直观。
- 暴露的症状：第二次工具调用依赖模型行为，无法由代码保证；摘要步骤失败时也可能没有稳定的成功卡片。
- 根因：把必须发生的业务后置动作误当成可选的 Agent 决策。
- 最终处理：Python 只发起一次挂号能力调用，由 Java service 明确执行“先挂号、后摘要”。

### 2. 编排曾下沉到错误的 Python 目录

- 当时的判断：将两次 HTTP 调用放进 `server-py/services` 可以保持工具函数简短。
- 暴露的症状：该目录按项目规则只允许知识检索/RAG；业务写流程仍滞留 Agent 层。
- 根因：只考虑了代码形状上的“薄壳”，没有先根据业务数据和事务所有权确定模块归属。
- 最终处理：删除 Python 业务编排 service，把流程归入 server-java `AppointmentService`。

### 3. 内部回调被误认为天然可信

- 当时的判断：Agent 回调是服务间内部接口，可以直接接受患者和会话标识。
- 暴露的症状：调用方能够伪造上下文；第一次补救还提供了可工作的默认密钥。
- 根因：将网络位置等同于身份认证，并忽略“缺少密钥时应启动失败”的安全配置原则。
- 最终处理：双向回调统一验证 `AGENT_CALLBACK_SECRET`，生产配置无可工作默认值，测试密钥只存在测试配置。

### 4. 幂等只覆盖写次数，没有覆盖返回语义

- 当时的判断：同一患者和排班有唯一约束且不再次扣号，就已经满足幂等。
- 暴露的症状：跨会话重试能返回已有挂号，但摘要回写因会话不匹配失败，随后把已存在的摘要误报为“暂未发送”。
- 根因：只验证了资源数量，没有验证重复请求是否返回与首次成功等价的状态。
- 最终处理：已有完整挂号结果原样短路，不重写旧摘要；真实摘要失败才返回降级提示。

### 5. 验证命令制造了噪音

- 当时的判断：直接使用通配符和正则过滤批量检查小程序 JavaScript。
- 暴露的症状：PowerShell 正则转义错误产生大量无关异常；Windows 未展开 Node 测试通配符，出现误导性的 `0 tests`。
- 根因：没有先确认目录、测试脚本和当前 shell 的参数展开规则。
- 最终处理：先枚举真实文件，再逐个执行语法检查；分别报告“自动化测试数量”和“语法检查文件数量”。

## 最终原则

- 业务写入的所有权优先于调用方便性：挂号状态、号源和摘要均由 server-java 定义失败语义。
- 必须发生的业务动作不能依赖 LLM 是否再次调用工具。
- 多步骤写流程要先声明提交点；后置步骤失败时，不得伪装或回滚已经提交的事实。
- 幂等验收同时检查资源计数、状态和响应语义。
- 携带用户身份上下文的服务间接口必须鉴权，且生产密钥缺失时应失败。
- 验证结果必须说明实际执行了多少测试或检查了多少文件，`0 tests` 不能被当成通过证据。

## 给 AI 的开工检查项

- [ ] 哪个服务拥有将被修改的数据和事务？
- [ ] 工具是否只是校验与转发，还是偷偷承担了业务状态机？
- [ ] 哪一步成功后不可逆？后续失败时用户会看到什么？
- [ ] 是否有任何必需步骤依赖模型自觉再次调用工具？
- [ ] 重复请求、跨会话重试和部分成功分别返回什么？
- [ ] 内部接口接受身份字段时，调用方如何被认证？缺少密钥时是否立即失败？
- [ ] 并发测试是否同时断言 Redis 和 PostgreSQL 的最终状态？
- [ ] 验证命令是否真的发现并执行了目标测试或文件？

## 规则改进候选

建议在分层纪律中补充：涉及业务写入的多步骤流程由 server-java service 原子化或显式编排，并向 Agent 暴露单一业务能力接口。该建议在正式修改 `AGENTS.md` 或新增 ADR 前，仅作为复盘结论。

## 证据

- server-java 全量测试 96 项通过，其中覆盖最后一个号源的并发竞争、重复取消、幂等返回和摘要失败降级。
- server-py 全量测试 19 项通过，Ruff 与 mypy 通过。
- 支付宝开发者工具完成普通编译以及 AI 首页、“我的挂号”空状态和返回链路检查；仅出现本地 HTTP 开发警告。
- 最终 Standards 与 Spec 双轴复审均为零发现。
