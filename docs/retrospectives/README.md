# 工程复盘库

这里记录 issue 实施过程中值得复用的碰壁经验，供人学习，也供 AI 在开工和审查前检索。目标不是追责或保存完整施工日志，而是把返工转化为下一次可执行的判断规则。

## 什么时候记录

满足任一条件时新增或更新复盘：

- 架构或目录归属发生实质返工；
- 安全、权限、隐私或一致性边界在后期才被发现；
- 实现“能跑”，但不满足确定性、幂等性或失败语义；
- 验证命令产生假阳性、假阴性或大量误导噪音；
- 同一问题经过两轮以上审查才收敛；
- 形成了能显著降低后续试错的检查清单。

普通拼写修复、一次性环境波动和没有复用价值的细节不记录。

## 人和 AI 如何使用

开工前：

1. 按 issue、领域和标签查下面的索引。
2. 阅读相关复盘的“最终原则”和“开工检查项”。
3. 若原则需要成为强制约束，检查它是否已进入 `AGENTS.md` 或 ADR；不能把复盘本身当作架构宪法。

交付前：

1. 区分事实、判断失误、环境噪音和审查发现。
2. 记录失败路径为什么看似合理，以及什么证据推翻了它。
3. 把教训写成可回答“开工前应该检查什么”的条目。
4. 使用 [`TEMPLATE.md`](TEMPLATE.md)，避免粘贴完整对话流水。

## 记录边界

- 不记录患者敏感原文、真实凭据或可识别个人的信息。
- 不把聊天记录、命令输出和审查意见原样倾倒进文档。
- 不把“这次这样修了”直接提升为通用规则；必须说明适用范围。
- 复盘可以提出宪法或 ADR 的候选修改，但是否采纳必须单独决策。
